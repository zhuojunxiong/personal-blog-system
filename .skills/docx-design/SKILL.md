# DOCX Design Skill

状态：v1.0 课程交付

用途：将 Markdown 设计文档整理为课程提交所需的概要设计文档，输出适合答辩和提交的结构化材料。

## 触发短语

说出以下任一即可触发本 Skill：
- "prepare design doc" / "整理设计文档" / "导出设计说明书"
- "准备概要设计交付" / "整理架构说明给老师"
- "generate design document"

## 触发场景

- 课程提交前需要将 `docs/08_概要设计说明书.md` 整理为正式交付文档
- 答辩前需要确认设计文档与代码实现一致
- 架构或模型变更后需要同步更新设计说明书

## 工作步骤

### 步骤 1：读取输入材料
按以下顺序读取，后者用于校验前者是否与代码事实一致：

| 顺序 | 文件 | 用途 |
| --- | --- | --- |
| 1 | `AGENTS.md` | 确认当前分支 `work/v1.0-course-delivery`、技术栈约束（Flask+Jinja2+SQLAlchemy+SQLite）、禁止事项 |
| 2 | `docs/08_概要设计说明书.md` | 设计文档主体——系统边界、模块划分、接口设计、数据模型 |
| 3 | `docs/03_v0.5.1架构追溯.md` | 架构基线——v0.5.1 时期的架构事实，用于对比 v1.0 的变化 |
| 4 | `app/models.py` | 代码事实源——校验设计文档中的数据模型描述是否与实际代码一致 |
| 5 | `app/__init__.py` | 代码事实源——校验蓝图注册、扩展初始化、错误处理是否与设计描述一致 |

### 步骤 2：逐项核对
- **系统边界**：Flask 应用、11 个 Blueprint、SQLite 数据库、Jinja2 模板引擎 —— 是否都在设计文档中有描述。
- **模块划分**：public/auth/admin/dashboard/article/column/category/tag/comment/ai/user —— 每个模块的职责描述是否准确。
- **数据模型**：9 个模型类 + 1 个关联表 —— 字段、关系、约束是否与 `app/models.py` 一致。
- **路由设计**：各 Blueprint 的路由是否在文档中有说明。
- **标注差异**：如发现文档与代码不一致，在输出中标注"需人工确认"并说明差异点。

### 步骤 3：整理设计文档
基于核对结果，输出设计文档的三个核心部分：
1. **架构概述**：技术栈、系统分层、模块关系图（引用 `diagrams/plantuml/` 中的图）
2. **模块设计**：每个 Blueprint 的职责、关键路由、依赖
3. **数据模型**：ER 关系说明、关键表结构、索引策略

### 步骤 4：记录使用日志
在 `docs/skills-usage/skill_usage_log.md` 中追加一行：

```
| YYYY-MM-DD | work/v1.0-course-delivery | 文档任务 | docx-design Skill | docs/08_概要设计说明书.md, docs/03_v0.5.1架构追溯.md, app/models.py | [输出文件] | 是/否 | N/A | [差异点或确认事项] |
```

## 输出格式（告知用户）

```
## 设计文档整理结果

- 输入文件：docs/08_概要设计说明书.md, docs/03_v0.5.1架构追溯.md, app/models.py
- 核对结论：[一致 / 发现 N 处差异]
- 差异清单：
  1. [文档说 X，代码是 Y]
- 架构概述：[已整理/需补充]
- 模块设计：[已整理/需补充]
- 数据模型：[已整理/需补充]
- 记录位置：docs/skills-usage/skill_usage_log.md
- 需人工确认：[具体项]
```

## 禁止事项

1. 不更换 Flask+Jinja2+SQLAlchemy+SQLite 技术路线。
2. 不把设计建议写成已实现——区分"已实现""已设计未实现""计划中"。
3. 不生成 docx 文件时伪造结果——未执行就写"未导出"。
4. 不复制教师资料全文。
5. 不提交 jar、字体、缓存或无关二进制资源。
