# DOCX Requirement Skill

状态：v1.0 课程交付

用途：将 Markdown 需求文档和变更请求整理为课程提交所需的需求规格文档，产出适合答辩和提交的结构化材料。

## 触发短语

说出以下任一即可触发本 Skill：
- "prepare requirement doc" / "整理需求文档" / "导出需求规格说明书"
- "准备需求交付" / "整理需求追溯给老师"
- "generate requirement document"

## 触发场景

- 课程提交前需要将需求规格和追溯信息整理为正式交付文档
- 答辩前需要确认需求文档与 CR 记录、代码实现一致
- 新增 CR 后需要将变更纳入需求文档

## 工作步骤

### 步骤 1：读取输入材料
按以下顺序读取，尊重代码事实优先级：

| 顺序 | 文件 | 用途 |
| --- | --- | --- |
| 1 | `AGENTS.md` | 确认当前分支、信息可信度优先级（代码 > 正式文档 > README） |
| 2 | `docs/07_需求规格说明书.md` | 需求文档主体——功能需求（F001-F050）、非功能需求（N001-N012）、验收标准 |
| 3 | `docs/02_v0.5.1需求追溯.md` | 需求基线——v0.5.1 时期的需求事实，用于对比 v1.0 的变化 |
| 4 | `docs/change-requests/CR-*.md` | 所有 CR 记录——了解 v0.5.1 到 v1.0 的需求变更历史 |

### 步骤 2：逐项核对
- **功能需求 F001-F050**：每一项是否在 CR 中有变更记录；是否与当前代码实现一致。
- **非功能需求 N001-N012**：每一项的状态（已实现/部分实现/计划中/需人工确认）。
- **CR 追溯**：自 v0.5.1 以来所有 CR 是否在需求文档中有体现；变更结论（已确认/暂缓/拒绝）是否明确。
- **标注差异**：如发现文档与 CR 或代码不一致，在输出中标注"需人工确认"。

### 步骤 3：整理需求文档
基于核对结果，输出需求文档的三个核心部分：
1. **需求概述**：系统定位（AI 驱动的知识写作与搜索平台）、用户角色、核心场景
2. **功能需求清单**：F001-F050 按模块分组，标注实现状态
3. **变更追溯**：CR 列表及对应功能需求映射

### 步骤 4：记录使用日志
在 `docs/skills-usage/skill_usage_log.md` 中追加一行：

```
| YYYY-MM-DD | work/v1.0-course-delivery | 文档任务 | docx-requirement Skill | docs/07_需求规格说明书.md, docs/02_v0.5.1需求追溯.md, docs/change-requests/ | [输出文件] | 是/否 | N/A | [差异点或确认事项] |
```

## 输出格式（告知用户）

```
## 需求文档整理结果

- 输入文件：docs/07_需求规格说明书.md, docs/02_v0.5.1需求追溯.md, docs/change-requests/ (共 N 个 CR)
- 核对结论：[一致 / 发现 N 处差异]
- 功能需求状态：
  - 已实现：X 项
  - 部分实现：Y 项
  - 计划中：Z 项
  - 需人工确认：W 项
- CR 变更追溯：[列表]
- 记录位置：docs/skills-usage/skill_usage_log.md
- 需人工确认：[具体项]
```

## 禁止事项

1. 不伪造需求实现状态——未实现就是"未实现"或"计划中"。
2. 不把未执行的 docx 导出写成已完成。
3. 不覆盖当前代码事实——如果代码与文档冲突，以代码为准并标注差异。
4. 不复制教师模板全文。
5. 不提交无关二进制资源。
