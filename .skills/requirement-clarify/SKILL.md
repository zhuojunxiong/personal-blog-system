# Requirement Clarify Skill

状态：v1.0 课程交付

用途：当有新功能提议或范围变更时，澄清需求、收敛范围、评估影响，产出或更新一份 CR（变更请求）。

## 触发短语

说出以下任一即可触发本 Skill：
- "clarify this requirement" / "需求澄清" / "帮我澄清这个需求"
- "新功能评估" / "这个需求该不该做" / "写一份变更请求"
- "scope this" / "收敛范围"

## 触发场景

- 用户提出新功能、页面改版、流程变更
- 发现现有需求描述模糊，需要拆解和明确验收标准
- 课程交付前需要判断某个功能是否应纳入 v1.0 范围
- 需要写入正式 CR 供后续设计、开发和审查使用

## 工作步骤

### 步骤 1：读入上下文
- 读取 `AGENTS.md`，确认当前分支 `work/v1.0-course-delivery`、阶段定位和禁止事项。
- 读取 `docs/02_v0.5.1需求追溯.md`，确认现有需求基线（F001-F050, N001-N012），判断新需求是否与已有需求冲突或重叠。

### 步骤 2：检查是否已有 CR
```bash
ls docs/change-requests/CR-*.md
```
- 如有标题或内容匹配现有 CR，先读取该 CR，判断是补充还是新开。
- 如无匹配，按顺序分配下一个 CR 编号（如 CR-011）。

### 步骤 3：使用 CR_TEMPLATE.md 起草
读取 `docs/change-requests/CR_TEMPLATE.md`，填写以下关键章节：

| 章节 | 填写要点 |
| --- | --- |
| 1. 变更编号 | CR-XXX，状态初始为"待确认" |
| 2. 变更标题 | 一句话概括 |
| 3. 变更背景 | 触发来源、当前问题或机会 |
| 4. 涉及需求编号 | 是否影响已有 F001-F050 / N001-N012 |
| 5. 涉及页面/模块 | 路由、模板、模型、脚本 |
| 6-10. 影响评估 | 产品、设计、数据库、测试、文档影响 |
| 11. 是否需要 ADR | 架构变更 → 需要；纯功能 → 不需要 |
| 12. 验收标准 | 可验证的通过条件（用户可见的行为） |
| 13. 是否允许进入实现 | 初始值"待确认"，须人工确认后改为"允许" |
| 14. 人工确认 | 留空，待项目负责人填写 |

### 步骤 4：输出
- 新 CR 文件保存到 `docs/change-requests/CR-XXX-[标题].md`。
- 总结要点告知用户：范围结论、纳入/不纳入、需人工确认项。

## 输出格式（告知用户）

```
## 需求澄清结果

- CR 编号：CR-XXX
- 背景：[一句话]
- 纳入范围：[列表]
- 不纳入范围：[列表]
- 验收标准：[列表]
- 是否需要 ADR：[是/否，理由]
- 影响文档：02_需求追溯 / 07_需求规格 / 08_概要设计 / 09_测试报告
- 需人工确认：[具体项]
```

## 禁止事项

1. 不写业务代码——本 Skill 只产出 CR 文档。
2. 不擅自修改 CR 状态为"已确认"或"允许"——这属于人工确认。
3. 不把未来版本计划写成 v1.0 范围。
4. 不读取或修改 `software-practice-records`。
