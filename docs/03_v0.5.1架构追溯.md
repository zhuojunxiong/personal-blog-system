## 2. 当前自然形成的架构

当前系统是一个服务端渲染的 Flask 单体应用。它不是微服务架构，也不是前后端完全分离架构；自然形成的边界是“蓝图模块 + 服务类 + 统一模型 + Jinja 模板 + 少量前端脚本”。

当前系统分层如下：

| 分层 | 当前实现 | 职责 | 代表依据 |
|---|---|---|---|
| 启动与配置层 | `run.py`、`config.py`、`app/__init__.py` | 创建 Flask app，加载配置，初始化扩展，注册蓝图、错误处理和模板 helper。 | F038, F040, F044, F047 |
| 扩展层 | `app/extensions.py` | 统一持有 `db`、`login_manager`、`csrf` 等 Flask 扩展实例。 | F038, F039, F043 |
| 路由/控制层 | `app/*/routes.py` | 接收请求，做登录/权限校验，调用 service 或 ORM，返回模板或 JSON。 | F001-F034, F042 |
| 业务服务层 | `app/*/services.py`、`app/services.py` | 承载文章、认证、用户、分类、标签、专栏、评论、AI、仪表盘等业务逻辑。 | F007-F034 |
| 数据模型层 | `app/models.py` | 定义数据库表、字段、关系、唯一约束和模型属性。 | F039-F041 |
| 模板展示层 | `app/templates/` | 使用 Jinja2 生成前台、个人中心、后台、错误页。 | F001-F025, F034, F047 |
| 静态资源层 | `app/static/css/`、`app/static/js/` | 组织全局样式、v041 页面样式和前端交互。 | F032, F043, F048 |
| 外部服务适配层 | `app/ai/services.py` | 封装 OpenAI 兼容接口调用、异常转换、智能搜索编排。 | F026-F032, F044-F046 |
| 数据初始化和测试辅助层 | `scripts/`、`test_e2e.py` | 提供初始化、演示数据和 E2E 脚本入口。 | F036, F037, F049 |

这套架构的实际风格是“轻量 MVC + Service 辅助”：路由接近 Controller，Jinja 模板接近 View，SQLAlchemy 模型接近 Model，service 负责复用逻辑和部分事务提交。

## 4. 路由组织

当前路由按 Blueprint 拆分，但 URL 前缀并不完全等同于模块目录。有些模块同时包含公开端、个人端和后台端路由，这是当前自然形成的组织方式。

| Blueprint | URL 组织 | 主要入口 | 支撑需求 |
|---|---|---|---|
| `public` | 无统一前缀 | `/`、`/home`、`/discover`、`/articles`、`/articles/<slug>`、`/categories`、`/tags`、`/search` | F001-F007, F035 |
| `auth` | 无统一前缀 | `/login`、`/admin/login`、`/register`、`/logout` | F008, F009 |
| `admin` | `/admin` | `/admin/` 跳转后台仪表盘 | F021 |
| `dashboard` | `/admin` | `/admin/dashboard` | F021 |
| `article` | `/admin/articles` | 后台文章列表、新增、编辑、删除 | F016 |
| `category` | `/admin/categories` | 后台分类管理 | F023 |
| `tag` | `/admin/tags` | 后台标签管理 | F024 |
| `comment` | 混合 | `/articles/<slug>/comments`、`/articles/<slug>/like`、`/articles/<slug>/favorite`、`/admin/comments` | F017-F020 |
| `column` | 混合 | `/columns`、`/columns/<id>`、`/my/columns`、`/admin/columns` | F005, F013, F025 |
| `ai` | 混合 | `/admin/ai`、`/ai/status`、`/ai/summary`、`/ai/tags`、`/ai/polish`、`/ai/chat`、`/ai/outline`、`/ai/titles`、`/ai/search` | F026-F034 |
| `user` | 混合 | `/users/<id>`、`/profile`、`/settings`、`/write`、`/my/articles/...`、`/admin/users` | F006, F010-F012, F014, F015, F022 |

架构观察：

1. 后台路由分散在 `article`、`category`、`tag`、`comment`、`column`、`user`、`ai` 等模块中，统一依赖 `admin_required()`。
2. 个人创作路由主要位于 `user` 模块，文章业务逻辑复用 `ArticleService`。
3. 互动路由归入 `comment` 模块，但点赞、收藏实际调用 `ArticleService`。
4. AI 写作接口要求登录，AI 智能搜索 `/ai/search` 是公开 JSON 端点。
5. AI JSON 接口使用 `@csrf.exempt`，前端仍会注入 CSRF header；该安全口径需人工确认是否符合后续治理要求。

## 5. 数据库模型关系

当前模型集中在 `app/models.py`，属于单文件模型层。

| 模型 | 表 | 核心关系 | 支撑需求 |
|---|---|---|---|
| `User` | `users` | 用户拥有文章、专栏、评论、点赞、收藏；通过 `role` 区分管理员。 | F008-F012, F021, F022, F041, F042 |
| `BlogColumn` | `blog_columns` | 多个专栏属于一个用户，一个专栏关联多篇文章。 | F005, F013, F025 |
| `Category` | `categories` | 一个分类关联多篇文章。 | F003, F014, F016, F023 |
| `Tag` | `tags` | 通过 `ArticleTag` 与文章多对多。 | F004, F014, F016, F024 |
| `ArticleTag` | `article_tags` | 文章与标签的关联表，复合主键。 | F004, F014, F024 |
| `Article` | `articles` | 文章属于用户、分类、可选专栏；关联标签、评论、AI 日志。 | F001-F007, F014-F016, F019, F020 |
| `Comment` | `comments` | 评论属于文章，可选属于用户；状态包括 pending/approved/hidden。 | F017, F018 |
| `Like` | `likes` | 用户与文章点赞关系，`user_id + article_id` 唯一。 | F019 |
| `Favorite` | `favorites` | 用户与文章收藏关系，`user_id + article_id` 唯一。 | F020 |
| `AiLog` | `ai_logs` | 可选关联文章，记录 AI 场景、输入、输出和采纳字段。 | F033 |

主要关系可以概括为：

```text
User 1 ── * Article
User 1 ── * BlogColumn
BlogColumn 1 ── * Article
Category 1 ── * Article
Article * ── * Tag，通过 ArticleTag
Article 1 ── * Comment
User 1 ── * Comment
User * ── * Article，通过 Like
User * ── * Article，通过 Favorite
Article 1 ── * AiLog
```

当前数据层对需求的支撑：

1. 内容浏览和检索依赖 `Article`、`Category`、`Tag`、`BlogColumn`、`User`，支撑 F001-F007。
2. 用户创作依赖 `User`、`Article`、`BlogColumn`、`Category`、`Tag`，支撑 F013-F016。
3. 互动依赖 `Comment`、`Like`、`Favorite`，其中唯一约束支撑 F019-F020。
4. AI 日志依赖 `AiLog`，但 `adopted_result/is_adopted/problem_found` 暂未见完整写入流程，F033 日志完整性需人工确认。
5. 当前没有 `ReadingHistory`、关注、私信、付费、广告、热榜等模型，因此不能把这些能力写成当前架构。

当前 JS 数据流：

1. 普通搜索表单校验空输入后走 GET `/search`，支撑 F007。
2. AI 搜索表单拦截 submit，POST JSON 到 `/ai/search`，成功后渲染 AI 搜索结果，失败后跳转普通 `/search` 降级，支撑 F032。
3. `base.html` 自动为 POST 表单注入 CSRF 隐藏字段，并包装 `fetch` 自动附加 `X-CSRFToken`，支撑 F043。
4. 阅读页 AI 辅助按钮只做后续开放提示，不能视为 AI 阅读助手实现，关联 F035。

## 8. 核心业务流程

### 8.1 游客浏览和阅读流程

```text
浏览器 GET /home 或 /discover 或 /articles
-> public 路由
-> ArticleService / CategoryService / TagService / ColumnService 查询
-> SQLAlchemy 读取 SQLite
-> Jinja 模板渲染
-> 浏览器展示文章、分类、标签、专栏等内容
```

支撑需求：F001、F003-F007。

文章详情流程：

```text
浏览器 GET /articles/<slug>
-> public.article_detail()
-> ArticleService.get_published_by_slug()
-> ArticleService.increment_view()
-> 路由拆分正文为 content_blocks 和 toc_items
-> v041/article_reading.html 渲染阅读页
```

支撑需求：F002。阅读页 AI 提示按钮属于 F035 后续计划，不是当前 AI 阅读助手。

### 8.2 注册、登录和权限流程

```text
用户提交注册/登录表单
-> auth 路由
-> AuthService 或 User.check_password()
-> Flask-Login 写入登录态
-> current_user 在后续请求中参与权限判断
```

支撑需求：F008、F009、F041。

后台权限流程：

```text
浏览器访问 /admin/*
-> 对应路由使用 @admin_required
-> 未登录跳转管理员登录
-> 非管理员 abort(403)
-> 管理员进入后台页面
```

支撑需求：F021、F022、F042。

### 8.3 普通用户创作流程

```text
登录用户 GET /write
-> user._write_article_form()
-> 查询分类、标签、个人专栏
-> 渲染 user/write.html

登录用户 POST /write 或 /my/articles/<id>/edit
-> 权限校验
-> ArticleService.validate()
-> ArticleService.create() 或 update()
-> 写入 Article、ArticleTag 等数据
-> 草稿返回编辑页，发布跳转文章详情
```

支撑需求：F013-F015、F026-F031。

### 8.4 评论、点赞和收藏流程

评论：

```text
登录用户 POST /articles/<slug>/comments
-> comment.submit()
-> ArticleService.get_published_by_slug()
-> CommentService.create_pending()
-> 写入 Comment，默认 pending
-> 管理员在 /admin/comments 审核
```

支撑需求：F017、F018。

点赞/收藏：

```text
登录用户 POST /articles/<slug>/like 或 /favorite
-> comment 路由
-> ArticleService.toggle_like() 或 toggle_favorite()
-> 检查 Like/Favorite 是否已存在
-> 新增或删除关联，并更新计数
```

支撑需求：F019、F020。

### 8.5 后台治理流程

```text
管理员访问 /admin/dashboard
-> DashboardService.stats()
-> 渲染后台统计

管理员访问文章、用户、专栏、分类、标签、评论、AI 页面
-> 对应模块路由 + @admin_required
-> 调用 service 或 ORM
-> 渲染 admin 模板
```

支撑需求：F016、F021-F025、F034。

### 8.6 AI 写作辅助流程

```text
登录用户在写作页触发 AI 操作
-> 前端 POST JSON 到 /ai/summary、/ai/tags、/ai/polish、/ai/chat、/ai/outline、/ai/titles
-> ai 路由校验登录和可访问文章
-> AIService 组装 OpenAI 兼容 Chat Completions 请求
-> requests 调用远程 AI 服务
-> 成功或失败都通过 _log() 写入 AiLog 基础字段
-> 返回 JSON 给前端
```

支撑需求：F026-F031、F033、F044-F046。

需人工确认：

1. 当前代码接口存在，但本次未配置 API Key、未启动服务、未调用远程 API，F026-F031 的真实远程调用需验证。
2. `_log()` 只写入 `scene/input_text/ai_output/article_id`，F033 中 `adopted_result/is_adopted/problem_found` 的完整采纳和问题记录流程需人工确认。

### 8.7 AI 智能搜索流程

```text
用户在首页或搜索页提交 AI 搜索
-> v041.js POST /ai/search
-> AIService.smart_search()
   -> 阶段 1：search_intent_and_expand() 调远程 AI 理解意图和扩展关键词
   -> 阶段 2：_sql_multi_keyword_search() 用 SQL 取候选文章
   -> 阶段 3：rerank_with_reasons() 调远程 AI 重排序和生成理由
   -> 若阶段 1 或阶段 3 AI 调用失败，按代码逻辑降级
-> ai.routes._log() 写入搜索日志摘要
-> 前端渲染 AI 搜索结果；请求失败则跳转普通搜索
```

支撑需求：F032、F033、F045、F046。

需人工确认：

1. `/ai/search` 接口存在且服务编排存在，但真实远程 API 调用需验证。
2. F032 所属版本口径与 `v0.5.1` / `V5.1` 命名关系需人工确认。

## 9. 数据流说明

### 9.1 服务端渲染数据流

```text
HTTP 请求
-> Flask Blueprint route
-> Flask-Login / admin_required / CSRF
-> Service 或 SQLAlchemy 查询
-> SQLAlchemy Model
-> SQLite
-> Jinja2 Template
-> HTML 响应
```

主要覆盖 F001-F025、F034、F047。

### 9.2 写入型表单数据流

```text
HTML 表单 POST
-> base.html/admin/base.html 注入 csrf_token
-> Flask CSRFProtect 校验
-> route 收集 request.form
-> service validate
-> db.session.add/delete/commit
-> flash + redirect
```

主要覆盖 F008-F020、F023-F025、F041-F043。

### 9.3 AI JSON 数据流

```text
前端 fetch POST JSON
-> /ai/* route
-> @login_required 或公开搜索端点
-> AIService
-> requests.post(远程 Chat Completions API)
-> 解析 JSON 或转换异常
-> AiLog 基础记录
-> JSON 响应
```

主要覆盖 F026-F034、F044-F046。真实远程调用成功需人工确认。

## 11. 当前架构优点

1. 分层简单，适合课程实践和快速演示：Flask 单体、Jinja 模板、SQLite 能降低部署和理解成本，支撑 F001-F025。
2. Blueprint 已形成清晰模块入口：公开页、认证、用户、文章、专栏、分类、标签、评论、后台、AI 各有独立路由文件，支撑 F038。
3. 业务 service 已经承担复用逻辑：文章查询、创建更新、点赞收藏、评论审核、分类标签校验、AI 调用等不完全堆在路由中。
4. 数据模型覆盖当前核心域：多用户、文章、专栏、分类、标签、评论、点赞、收藏、AI 日志可以支撑 F001-F034。
5. 权限边界基本明确：普通登录用 `login_required`，后台用 `admin_required`，用户文章编辑删除有所有者校验，支撑 F015、F022、F042。
6. AI 能力被封装在单独 service：远程调用、场景参数、异常转换、搜索编排集中在 `AIService`，有利于后续替换模型或增强降级，支撑 F026-F032、F044-F046。
7. 前台和后台模板基座分开：`base.html` 与 `admin/base.html` 避免后台布局影响前台体验。
8. 需求追溯和架构追溯可以直接映射代码：F001-F050 已能关联到路由、service、模型、模板或文档状态。

## 15. 适合局部重构的地方

以下内容适合在后续有明确需求、测试保护和 ADR 或设计说明后进行局部重构；本次不执行：

1. 路由边界重整：将后台用户管理从 `user` 模块、后台专栏/评论/AI 路由从混合模块中逐步拆出或建立清晰命名约定。
2. Service 收敛：把 `public.search()`、`user.talk()`、`_personal_space_context()` 中较多 ORM 查询收敛到对应 service。
3. 模型拆分：当模型继续增加时，可从单个 `app/models.py` 拆成 `user/models.py`、`article/models.py` 等，但需处理导入和迁移风险。
4. 前端脚本拆分：将 `v041.js` 中确认框、Flash、搜索、AI 搜索、阅读页提示拆成更小模块，需确认当前构建方式是否仍保持无打包。
5. CSS 分层：将后台样式、公共组件、v041 页面样式拆分为更清晰的文件，避免 `main.css` 与 `v041.css` 长期重叠。
6. AI Provider 抽象：在确认后续会接入多 Provider 或更多模型时，可把 `AIService._call()` 抽出 provider adapter。
7. 事务边界梳理：复杂写入场景增加后，可减少 service 内散落 commit，形成更一致的事务策略。

## 16. 是否有必要探索新架构分支

当前结论：现阶段没有必要立即探索新架构分支。

理由：

1. 当前需求 F001-F034、F038-F047 主要是中小规模博客平台能力，现有 Flask 单体架构已经能直接支撑。
2. v0.5.1 阶段的重点是统一主仓库和工程化治理，F050 更需要补齐事实追溯、测试记录和设计文档，而不是更换技术栈。
3. 当前未验证的问题主要是 AI 真实调用、测试结果、视觉一致性、版本口径和日志完整性，属于验证与治理问题，不是必须换架构才能解决的问题。
4. 若未经确认探索前后端分离、微服务或异步任务架构，容易偏离 `AGENTS.md` 中“不允许未经确认更换技术栈”“不允许无关重构”的约束。

适合未来探索新架构分支的触发条件：

1. 需要正式支持移动端或第三方客户端，服务端渲染无法满足 API 复用。
2. AI 调用需要异步队列、流式输出、成本审计、多模型路由和长期任务。
3. 搜索从 SQL 模糊匹配升级为全文检索、向量检索或混合检索。
4. 用户、内容、互动数据规模明显超过 SQLite 和当前单体部署的舒适区。
5. 项目目标从课程实践演示升级为生产级多人平台。

在这些条件出现前，建议继续采用“现有单体架构 + 局部重构 + 文档和测试补齐”的路线。
