## 1. 产品定位

当前项目已经从早期个人博客演进为“AI 驱动的知识写作与搜索平台”。从当前需求和架构看，产品主线应调整为：

1. 读者以自然语言搜索知识内容。
2. 普通用户可注册、维护资料、创建知识合集、用 Markdown 写作、评论、点赞、收藏。
3. 管理员可做基础后台治理。
4. AI 能力承担资料搜索、大纲、润色、搜索摘要和智能搜索增强。
5. 发布后搜索摘要把“写作”和“被搜索到”连接成知识闭环。

产品方向判断：

- v0.5.1-governance：以统一主仓库、治理、验证、风险收敛为主。
- 产品重新基线化：基于半自动工程体系重新走一遍产品设计全流程。
- 下一实现版本：在产品重新基线化之后，再决定是 v0.6 稳定演进、v0.7 产品重构，还是 v1.0 课程交付版本；v0.6 只是候选之一。

## 7. 后续候选验证目标

以下内容可作为产品重新基线化后的候选验证目标；若下一实现版本选择 v0.6 稳定演进，可优先处理。目标不是扩张业务边界，而是把当前 v0.5.1 已有能力验证清楚、体验收稳、文档闭环。

建议目标：

1. 统一版本口径：完成 N001，明确 `v0.5.1` 与 `V0.5`、`V5.1`、`V0.4` 的关系，支撑 F032、F048-F050。
2. 验证启动链路：完成 N002，确认 F036、F049 当前可用性。
3. 建立测试报告：完成 N003，记录 F037 当前通过/失败结果，不引用历史测试结论替代当前结果。
4. 修正或记录错误路径风险：完成 N004，确认 F047 中 400 错误页风险。
5. 完成 AI 真实调用验证：完成 N005，覆盖 F026-F032、F045-F046。
6. 补 AI 日志闭环设计：完成 N006，明确 F033 后续实现边界。
7. 明确个人中心边界：围绕 F012 决定是否做真实最近阅读；如果做，应先设计 N007。
8. 做视觉一致性验收：完成 N008，确认 F048。
9. 校准 README 和启动指南：完成 N009，支撑 F049。
10. 补齐正式文档链路：推进 N012，支撑 F050。

后续候选阶段不建议目标：

1. 不做微服务、前后端分离或技术栈替换。
2. 不把 F035 AI 阅读助手作为必须完成项。
3. 不引入付费、私信、关注、热榜、推荐等新业务域。
4. 不在缺少测试保护时做大范围路由、模型或 CSS/JS 重构。

## 8. v1.0 建议目标

v1.0 建议定位：课程交付完整版。目标是形成“需求、设计、实现、测试、Review、AI 协作、总结”可追溯闭环，并保证演示路径稳定。

建议目标：

1. 产品闭环稳定：F001-F025 保持可用，普通用户和管理员的核心演示路径可稳定完成。
2. AI 能力有证据：F026-F032 完成真实调用验证或明确降级演示策略；F033 有清晰日志闭环或明确未实现说明；F034 可说明配置状态。
3. 工程治理闭环：F036-F050 均有当前证据或待确认说明，正式文档不再停留在骨架。
4. 测试和 Review 可追溯：F037、F050 形成测试报告、缺陷记录和代码 Review 记录。
5. 视觉和交互达标：F048 完成主要页面验收，记录未解决问题。
6. 可维护路线清楚：如果存在局部重构计划，需配套需求、设计、测试保护和 ADR。

v1.0 可评估的增强候选：

1. F012 的真实最近阅读。
2. F033 的 AI 采纳结果和问题标记。
3. F035 的 AI 阅读助手最小可用版本。
4. F007/F032 的搜索体验增强。
5. 后台治理说明和统计展示增强。

## 11. 可能需要局部重构的需求

以下方向不建议现在直接重构，但如果后续需求明确、测试保护到位，可以局部推进。

| 局部重构方向 | 关联需求 | 触发条件 |
|---|---|---|
| 路由边界重整 | F006, F010-F025, F034 | 后台用户、专栏、评论、AI 路由继续扩展导致职责混乱时。 |
| Service 收敛 | F007, F012 | 搜索、个人空间、交流页查询逻辑重复或难以测试时。 |

- 局部重构前应先明确需求和设计。
- 涉及架构边界变化时应补 ADR。
- 不应把局部重构伪装成当前治理分支或未确认下一实现版本必须完成的产品需求。

## 12. 未来才可能触发新架构分支的需求

当前结论：现阶段没有必要探索新架构分支。以下条件出现时，才建议通过 ADR 评估新架构。

| 触发条件 | 可能影响 | 当前处理 |
|---|---|---|
| 需要移动端、第三方客户端或开放 API | 可能推动前后端分离或 API 层设计 | 当前不纳入治理基线。 |
| AI 调用需要异步队列、流式输出、长期任务 | 可能引入任务队列、流式接口、状态查询 | 先完成 F026-F033 验证。 |
| 搜索升级为全文、向量或混合检索 | 可能引入搜索引擎或向量数据库 | 当前保留 F007/F032。 |
| 用户、内容、互动规模超出 SQLite 舒适区 | 可能需要生产数据库、迁移体系、缓存 | 当前仍以本地演示为主。 |
| 课程实践升级为生产级多人平台 | 可能需要部署、安全、审计、对象存储、监控 | 当前不提前设计。 |
| 付费、广告、私信、关注、问答社区等新业务域确定进入路线 | 可能引发领域模型拆分和后台治理扩展 | 当前暂不纳入。 |

## 13. 当前不建议做的事情

1. 不建议大规模重写现有系统。
2. 不建议默认更换 Flask、Jinja2、SQLite 或当前前端组织方式。
3. 不建议在没有 ADR 的情况下做架构分支探索。
4. 不建议把 F035 AI 阅读助手写成当前已实现。

6. 不建议把 F033 写成完整 AI 日志闭环，除非补齐采纳和问题标记流程。
7. 不建议直接引用历史“测试全部通过”作为当前 F037 事实。
8. 不建议从 `software-practice-records` 自动同步或迁移任何内容。
9. 不建议在产品重新基线化前引入付费、私信、关注、热榜、复杂推荐或问答社区。

## 15. 阶段性结论

当前最稳妥的产品路线是：

```text
v0.5.1-governance：统一事实源、补齐追溯、明确风险
-> 基于半自动工程体系重新走一遍产品设计全流程
-> 产品重新基线化后，再决定 v0.6 / v0.7 / v1.0 中的下一实现版本
```

在此路线下，现有 Flask + Jinja2 单体架构仍然适合在受控前提下继续演进。当前不应把精力放在大规模重写、技术栈切换或新架构分支上，而应优先处理 F036-F050 的工程治理闭环，并对 F026-F033 的 AI 能力给出可验证证据和清晰边界；v0.6 可以作为下一实现版本候选之一，但不能写成唯一确定路线。
