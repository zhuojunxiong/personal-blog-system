## 1. 决策背景

当前项目定位是“面向课程实践的多用户知识专栏博客系统”。根据现状盘点、需求追溯和架构追溯，当前系统已经形成以下事实：

1. F001-F025 已构成游客浏览、用户注册登录、用户创作、评论互动和管理员后台治理的主业务闭环。
2. F026-F032 的 AI 写作辅助和 AI 智能搜索接口已经存在，但真实远程调用仍需配置 API Key 后验证。
3. F033 AI 日志已有模型和基础写入，但采纳结果、是否采纳、问题标记等闭环仍需补设计或确认。
4. F036-F050 主要是初始化、测试、错误页、视觉一致性、启动文档和交付文档链路问题，属于 v0.5.1-governance 工程治理基线和后续候选验证重点。
5. 当前架构为 Flask 工厂函数 + Blueprint + Service + SQLAlchemy 模型 + Jinja2 模板 + SQLite + 少量原生 JS，不是微服务，也不是前后端分离。
6. `AGENTS.md` 明确要求架构变更先写 ADR，不允许未经确认更换技术栈，不允许无关重构，不允许破坏 v0.5.1 已有功能。

因此，本次技术路线决策的核心问题不是“是否选择看起来更高级的新架构”，而是“哪条路线最能支撑当前 v0.5.1-governance 工程治理基线，并为产品重新基线化后的 v0.6、v0.7 或 v1.0 下一实现版本保留决策空间”。

## 2. 评价口径

本文按以下维度评估 A-E 五条路线：

1. 对 F001-F050 及 N001-N012 未来需求的支撑程度。
2. 开发成本。
3. 学习成本。
4. 课程验收风险。
5. 对 v0.5.1 已有功能的影响。
6. 是否需要数据库迁移。
7. 是否需要大量重写页面。
8. 是否有利于文档和答辩。
9. 是否适合当前时间周期。
10. 主要风险。
11. 推荐程度。

推荐程度分为：

| 等级 | 含义 |
|---|---|
| 基准约束 | 作为后续路线的保守边界，不等同于最终采纳路线。 |
| 高 | 适合作为最终采纳路线，但必须满足测试保护、需求确认和 ADR 约束。 |
| 中 | 可作为受控补充或后续评估路线，需满足前置条件。 |
| 低 | 当前不建议作为主路线。 |
| 很低 | 当前应避免，除非需求和约束发生重大变化。 |

## 3. 路线 A：保留当前 Flask + Jinja2 + SQLite 单体架构，继续稳定演进

路线定义：保留现有技术栈和整体架构，不做大规模结构调整，优先完成启动、测试、AI 验证、视觉验收、文档链路和必要的小修小补。

| 评价维度 | 分析 |
|---|---|
| 对 F001-F050 及 N001-N012 的支撑程度 | 高。F001-F025 主链路已经由现有架构支撑；F026-F032 可在现有 `AIService`、AI 路由和前端入口上验证；F033 可先补日志闭环设计；F036-F050 与 N001-N012 多数是验证、文档和验收任务，不要求新架构。 |
| 开发成本 | 低。重点是验证、补文档、修小风险和少量体验调整，不需要重建业务域。 |
| 学习成本 | 低。延续 Flask、Jinja2、SQLAlchemy、SQLite 和当前目录组织，便于团队说明和答辩。 |
| 课程验收风险 | 低。主业务闭环已存在，路线目标与治理基线和后续稳定演进候选方向一致。 |
| 对 v0.5.1 已有功能的影响 | 最小。以保留 F001-F025、F038-F047 为前提，避免破坏已形成链路。 |
| 是否需要数据库迁移 | 默认不需要。若后续采纳 N007 `ReadingHistory` 或 F033 日志闭环新增字段，需另行设计并确认；当前路线本身不要求迁移。 |
| 是否需要大量重写页面 | 不需要。F048 可通过视觉验收和小范围修正处理，不需要重写模板体系。 |
| 是否有利于文档和答辩 | 高。有利于按 F001-F050、N001-N012 建立需求、架构、测试、Review、AI 协作记录，答辩时也能清楚说明“先稳定、再演进”的工程判断。 |
| 是否适合当前时间周期 | 高。最符合 v0.5.1-governance 的风险收敛目标。 |
| 主要风险 | 结构性问题会继续存在，例如模型单文件、部分蓝图职责混合、CSS/JS 较集中；但这些目前是可控维护问题，不是阻塞验收的问题。 |
| 推荐程度 | 基准约束。作为低风险保守边界，不作为最终采纳路线。 |

## 4. 路线 B：保留当前技术栈，进行局部重构

路线定义：保留 Flask + Jinja2 + SQLAlchemy + SQLite，但在明确需求、测试保护和 ADR 前提下，对局部结构进行收敛，例如路由边界、Service、模型拆分、CSS/JS 分层、AI Provider 抽象或事务边界整理。

| 评价维度 | 分析 |
|---|---|
| 对 F001-F050 及 N001-N012 的支撑程度 | 中到高。对 F007、F012、F033、F048、N006、N007、N011 等可维护性和体验增强有帮助；对 F001-F025 主链路不是必要前提。 |
| 开发成本 | 中。局部重构本身不换栈，但需要补测试、补设计、写 ADR，并承担回归成本。 |
| 学习成本 | 低到中。技术栈不变，但团队需要理解新的模块边界和重构意图。 |
| 课程验收风险 | 中。若没有测试保护，路由、模型、模板或事务调整可能破坏已有演示链路。 |
| 对 v0.5.1 已有功能的影响 | 取决于范围。小范围 Service 收敛或 CSS 整理影响较低；模型拆分、路由重整、事务调整影响较高。 |
| 是否需要数据库迁移 | 不一定。纯路由、Service、CSS/JS 整理不需要；新增 `ReadingHistory`、AI 日志质量字段或模型结构变化可能需要迁移，需人工确认。 |
| 是否需要大量重写页面 | 不应需要。若重构升级为模板体系重写，就已经偏离“局部重构”。 |
| 是否有利于文档和答辩 | 中到高。适量局部重构可以体现工程治理能力；但必须用 ADR、测试报告和 Review 记录解释收益、风险和回滚方式。 |
| 是否适合当前时间周期 | 高。适合作为测试保护、需求确认和 ADR 约束下的最终采纳路线，不适合作为 v0.5.1-governance 当前无边界任务。 |
| 主要风险 | 容易把“改善结构”扩展成无边界重构；若测试不足，可能用较高成本换来不可见收益。 |
| 推荐程度 | 高。最终采纳方案 B，但必须以测试保护、需求确认和 ADR 约束为前提；不等于立即重写、换栈或前后端分离。 |

局部重构前提：

1. 必须有明确需求或问题触发，例如 F012 需要真实最近阅读、F033 需要日志闭环、F048 验收发现 CSS 冲突、F007/F032 搜索逻辑难以测试。
2. 必须先补测试保护，至少覆盖被重构模块的核心路径和权限边界。
3. 涉及架构边界变化时必须补 ADR，说明背景、备选方案、决策、影响范围和回滚方式。
4. 不应把局部重构伪装成当前治理分支或未确认下一实现版本必须完成的产品需求。
5. 不应在缺少当前 E2E 结果和启动验证时做模型拆分、路由大挪动或事务策略调整。

## 5. 路线 C：旧架构稳定演进 + arch/v1-experiment 新架构有限探索

路线定义：在当前主仓库治理基线稳定后，另开 `arch/v1-experiment` 分支或目录，对新架构做有限探索。探索内容可能包括 API 化、前后端分离、异步 AI、搜索引擎或其他新技术。

| 评价维度 | 分析 |
|---|---|
| 对 F001-F050 及 N001-N012 的支撑程度 | 对主线支撑取决于是否保持当前能力和治理基线；对探索分支支撑当前需求有限。N001-N012 主要仍应在主线完成。 |
| 开发成本 | 高。需要同时维护稳定线和实验线，产生双份文档、双份验证和分支同步成本。 |
| 学习成本 | 中到高。团队需要理解现有架构和实验架构，答辩口径也更复杂。 |
| 课程验收风险 | 中到高。若探索分散精力，会影响 v0.5.1-governance 和 F036-F050 治理闭环。 |
| 对 v0.5.1 已有功能的影响 | 如果实验严格隔离，直接影响较低；如果反向合并不受控，影响较高。 |
| 是否需要数据库迁移 | 主线不需要；实验线视探索内容而定，可能需要迁移或数据映射，需人工确认。 |
| 是否需要大量重写页面 | 主线不需要；实验线如果探索前后端分离或新 UI，通常需要大量重写页面。 |
| 是否有利于文档和答辩 | 有条件有利。可以展示架构思考，但若缺少 ADR 和实验边界，会被质疑偏离课程交付目标。 |
| 是否适合当前时间周期 | 低到中。当前目标是完成工程治理基线，不是扩张架构探索。 |
| 主要风险 | 探索新架构被误解为当前必须执行；实验分支消耗时间；主线文档和测试反而补不齐；版本口径更混乱。 |
| 推荐程度 | 低。当前不建议立即执行；只有在主线稳定、测试报告和文档链路基本完成后，才可通过 ADR 做有限探索。 |

路线 C 的边界：

1. “探索新架构”不能写成当前必须执行，也不能写成当前已实现能力。
2. 若未来确实需要探索，应先写 ADR，并说明探索目标、验证问题、停止条件、不会影响主线交付的隔离方式。
3. 探索分支不应承诺替代当前主线，也不应作为 v1.0 默认路线。
4. 当前没有移动端 API、开放 API、异步 AI、全文/向量搜索或生产级部署的明确必做需求，因此缺少立即开启实验分支的必要性。

## 6. 路线 D：更换部分技术栈

路线定义：保留部分业务逻辑，但替换一个或多个关键技术组件，例如从 SQLite 切换到 MySQL/PostgreSQL，从 Jinja2 切换到现代前端框架，从 Flask 切换到 FastAPI/Django，或引入任务队列、搜索引擎、前端构建体系等。

| 评价维度 | 分析 |
|---|---|
| 对 F001-F050 及 N001-N012 的支撑程度 | 当前必要性低。F001-F050 与 N001-N012 大部分能由现有架构支撑；技术栈替换主要服务远期高并发、多客户端、复杂搜索、生产部署等当前暂缓方向。 |
| 开发成本 | 高。需要适配配置、数据访问、路由、模板、测试、部署和文档。 |
| 学习成本 | 中到高。新技术需要团队学习、调试和答辩说明。 |
| 课程验收风险 | 高。换栈会把风险从“验证现有能力”扩大为“重新证明基础能力可用”。 |
| 对 v0.5.1 已有功能的影响 | 高。登录、权限、CSRF、模板渲染、数据库关系、AI 接口和 E2E 都可能受影响。 |
| 是否需要数据库迁移 | 很可能需要。尤其是切换数据库或 ORM 组织方式时，需要迁移方案和回滚方案。 |
| 是否需要大量重写页面 | 如果替换 Jinja2 或引入前后端分离，通常需要大量重写页面；这与当前约束不匹配。 |
| 是否有利于文档和答辩 | 低到中。只有在有明确需求驱动时才有利；若没有需求支撑，容易被视为技术炫技或偏离课程验收。 |
| 是否适合当前时间周期 | 低。当前更需要完成 N001-N012 和 F036-F050 的证据闭环。 |
| 主要风险 | 换栈后出现功能回退、测试缺口、文档口径混乱、演示不稳定；还违反 `AGENTS.md` 中“未经确认不得更换技术栈”的约束。 |
| 推荐程度 | 很低。当前不建议立即更换技术栈。 |

当前不建议立即更换技术栈的原因：

1. `docs/03_v0.5.1架构追溯.md` 已确认现有 Flask + Jinja2 单体能支撑 F001-F034、F038-F047 的主要需求。
2. `docs/04_未来需求与产品方向.md` 将 v0.6 定位为候选下一实现版本之一，不是技术栈升级版，也不是唯一确定路线。
3. 当前待解决问题主要是版本口径、启动验证、测试报告、AI 真实调用、AI 日志闭环、视觉验收和文档链路，换栈不能直接解决这些问题。
4. 更换数据库、前端框架或后端框架会引入新的学习、迁移和回归风险。
5. `AGENTS.md` 明确禁止未经确认更换技术栈；若未来确实需要换栈，必须先有需求、设计、ADR、测试和回滚方案。

## 7. 路线 E：重新开发 v1.0

路线定义：以 v1.0 为目标重新开发系统，可能复制现有需求，也可能重新设计架构、数据模型、页面和交互。

| 评价维度 | 分析 |
|---|---|
| 对 F001-F050 及 N001-N012 的支撑程度 | 理论上可以重新支撑，但现实风险极高。需要重新实现 F001-F025 主业务闭环，并重新证明 F026-F050 和 N001-N012。 |
| 开发成本 | 极高。相当于放弃当前已形成的代码、模板、脚本和追溯关系。 |
| 学习成本 | 高。团队需要重新理解新架构、新代码和新问题。 |
| 课程验收风险 | 极高。重开发很可能导致已实现功能回退，且难以在当前周期补齐测试和文档证据。 |
| 对 v0.5.1 已有功能的影响 | 极高。F001-F025、F038-F047 需要重新实现或迁移，任何遗漏都会影响演示。 |
| 是否需要数据库迁移 | 通常需要。除非完全复用旧模型，但那又削弱了重开发的意义。 |
| 是否需要大量重写页面 | 需要。Jinja 模板、后台页面、个人中心、写作页、v041 页面大概率都要重做。 |
| 是否有利于文档和答辩 | 当前不利。答辩重点会从“系统已完成且可追溯”变成“为什么推翻已有可用系统”，解释成本很高。 |
| 是否适合当前时间周期 | 很低。与 v0.5.1-governance 工程治理基线和产品重新基线化前不锁定下一实现版本的口径冲突。 |
| 主要风险 | 功能回退、工期失控、测试不足、文档断链、版本口径更混乱、课程验收不稳定。 |
| 推荐程度 | 很低，当前不建议。 |

当前不建议大规模重写的原因：

1. 当前 F001-F025 主业务闭环已经存在，重写会让这些已实现能力重新进入不确定状态。
2. F038-F047 工程底座已经能支撑课程实践演示，当前主要短板是验证和文档闭环，不是架构无法承载。
3. F026-F033 的 AI 问题是“真实调用验证、降级、日志闭环”问题，不需要通过重写系统解决。
4. 产品重新基线化之前不锁定下一实现版本；无论后续选择 v0.6、v0.7 还是 v1.0，都不应以重写替代验证、体验补齐、AI 验证和文档闭环。
5. v1.0 目标是课程交付完整版，不默认升级为生产级平台，也不要求重新开发。
