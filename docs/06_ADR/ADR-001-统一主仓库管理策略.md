# ADR-001 统一主仓库管理策略

## 1. 标题

从“双仓库协同”调整为“personal-blog-system 统一主仓库”。

## 2. 状态

提议，待人工确认。

本文是 v0.5.1 阶段的架构决策记录草案。本文只记录仓库管理和事实源策略，不修改业务代码，不迁移外部目录内容，不读取或修改 `software-practice-records`。

## 3. 背景

当前项目处于 `v0.5.1` 统一主仓库和工程化治理阶段。根据 `AGENTS.md`，`personal-blog-system` 从 `v0.5.1` 开始作为唯一主仓库，代码、需求、设计、测试、UML、AI 协作记录和交付材料应统一维护在当前仓库中。

此前项目材料存在“双仓库协同”或外部目录参考的可能性，尤其是 `software-practice-records` 可能包含历史记录或后续备份材料。但 `AGENTS.md` 已明确：`software-practice-records` 暂不作为当前事实源，只作为历史归档或 Windows 后续备份参考；不得自动同步、覆盖或迁移其中内容，除非用户明确提出并确认迁移范围。

`docs/05_技术路线决策报告.md` 进一步确认，当前 v0.5.1/v0.6 的重点不是扩大协作面或引入新架构，而是统一事实源、补齐追溯、明确风险、建立可验证的文档链路。若继续维持多个仓库共同承载当前事实，容易造成版本口径、需求状态、实现状态、测试记录和交付材料互相冲突。

因此，需要通过 ADR 明确仓库管理策略：当前阶段以 `personal-blog-system` 作为唯一主仓库，外部目录不自动参与当前事实判断。

## 4. 可选方案

### 方案 A：继续维持“双仓库协同”

同时维护 `personal-blog-system` 和 `software-practice-records`，两个位置都可能包含需求、设计、测试、协作记录和交付材料。

优点是可以保留历史材料和不同环境下的文件组织方式。缺点是需要持续同步、比对和解释差异；一旦两个仓库内容不一致，当前事实源会变得不清晰，课程交付材料也更容易出现版本口径冲突。

### 方案 B：以 `personal-blog-system` 为统一主仓库，外部目录作为历史归档或备份参考

当前项目事实、正式文档、代码、测试记录和交付材料统一维护在 `personal-blog-system`。`software-practice-records` 不直接参与当前事实判断，也不自动同步、覆盖或迁移。

优点是事实源清晰、追溯路径集中，符合 `AGENTS.md` 的统一主仓库规则，也更适合后续建立 `docs/06_ADR/`、测试报告、Review 记录和 AI 协作记录。缺点是需要人工确认是否有历史材料需要迁移，且在迁移前不能把外部目录中的内容写成当前已完成成果。

### 方案 C：以 `software-practice-records` 为主，`personal-blog-system` 仅保留代码

将文档、记录和交付材料主要维护在 `software-practice-records`，`personal-blog-system` 只作为代码仓库。

优点是如果外部目录已有完整历史材料，可能便于保留历史上下文。缺点是与当前 `AGENTS.md` 的统一主仓库规则冲突，会削弱代码、需求、设计、测试和交付材料之间的直接追溯关系，也会增加后续课程验收时的解释成本。

## 5. 最终决策

采用方案 B：从当前阶段开始，以 `personal-blog-system` 作为统一主仓库。

具体决策如下：

1. 当前项目事实以 `personal-blog-system` 中的当前代码和正式文档为准。
2. `docs/` 目录作为需求、架构、ADR、测试、Review、AI 协作记录和交付材料的正式承载位置。
3. `software-practice-records` 暂不作为当前事实源，只作为历史归档或后续备份参考。
4. 不自动读取、同步、覆盖或迁移 `software-practice-records` 内容。
5. 若未来确需迁移外部材料，必须先由人工确认迁移范围、目标路径、冲突处理方式和验收口径。

## 6. 决策理由

1. `AGENTS.md` 已明确 `personal-blog-system` 是 `v0.5.1` 开始的唯一主仓库。
2. `docs/05_技术路线决策报告.md` 将 v0.5.1 的核心任务定位为统一事实源、补齐追溯、明确风险和建立可追溯协作流程。
3. 当前 F001-F050 和 N001-N012 的追溯、验证、AI、视觉和文档闭环更适合集中维护在一个仓库中。
4. 双仓库协同会增加同步成本和事实冲突风险，尤其容易把历史材料、后续计划或外部备份误写成当前已实现能力。
5. 统一主仓库有利于后续 ADR、测试报告、Review 记录和 AI 协作记录逐步形成闭环。

## 7. 正面影响

1. 当前事实源更清晰，便于判断哪些内容已经存在、哪些内容待补齐、哪些内容需人工确认。
2. 文档链路更集中，便于从需求、架构、ADR、测试、Review 到总结形成可追溯路径。
3. 降低双仓库内容不一致带来的版本口径风险。
4. 降低误把外部历史材料写成当前实现或当前交付成果的风险。
5. 有利于 v0.6 稳定演示和 v1.0 课程交付材料整理。

## 8. 负面影响

1. 如果 `software-practice-records` 中确有有价值的历史材料，当前不会自动纳入，需要后续人工确认和迁移。
2. 统一主仓库后，所有正式材料都需要在 `personal-blog-system` 中补齐，短期内文档维护压力会集中到一个仓库。
3. 过去依赖外部目录的协作方式需要调整，团队成员需要统一使用当前仓库作为事实入口。
4. 若后续确需从外部目录迁移材料，仍需要处理重复、过时、冲突和格式不一致的问题。

## 9. 后续措施

1. 继续在 `personal-blog-system/docs/` 下补齐正式文档链路。
2. 后续新增 ADR 统一放入 `docs/06_ADR/`。
3. 后续测试报告、Review 记录、AI 协作记录和项目总结分别放入 `docs/09_测试报告.md`、`docs/10_代码Review记录.md`、`docs/11_AI协作记录.md`、`docs/12_项目总结.md` 或经人工确认的新路径。
4. 若发现当前仓库文档与代码事实冲突，应按 `AGENTS.md` 的信息可信度优先级处理，并标注“需人工确认”。
5. 若未来需要迁移 `software-practice-records` 中的材料，先单独建立迁移清单或迁移 ADR，不能直接覆盖当前仓库内容。

## 10. 待确认事项

1. 是否正式采纳 `personal-blog-system` 作为唯一主仓库，需人工确认。
2. `software-practice-records` 是否仅作为历史归档或备份参考，需人工确认。
3. 是否需要在后续某个阶段人工盘点 `software-practice-records` 中可迁移材料，需人工确认。
4. 若未来迁移外部材料，迁移范围、冲突处理规则和验收方式需人工确认。
5. 当前 ADR 的状态是否从“提议”调整为“已采纳”，需人工确认。
