# ADR-002 技术路线选择

## 1. 标题

采用“保留当前技术栈，在测试保护、需求确认和 ADR 约束下做受控局部重构”的技术路线。

## 2. 状态

已采纳。

本文基于 `docs/05_技术路线决策报告.md` 形成。本文只记录当前工程治理阶段的技术路线选择，不修改业务代码，不更换技术栈，不安装依赖，不把未来计划写成当前已实现能力。

## 3. 背景

当前项目定位是“面向课程实践的多用户知识专栏博客系统”。根据 `docs/05_技术路线决策报告.md`，当前系统已经形成游客浏览、用户注册登录、用户创作、评论互动和管理员后台治理的主业务闭环。AI 写作辅助和 AI 智能搜索接口已经存在，但真实远程调用仍需配置 API Key 后验证；AI 日志已有模型和基础写入，但采纳结果、是否采纳、问题标记等闭环仍需补设计或确认。

当前架构是 Flask 工厂函数、Blueprint、Service、SQLAlchemy 模型、Jinja2 模板、SQLite 和少量原生 JS 组成的服务端渲染单体应用。当前系统不是微服务，也不是前后端分离。

`docs/05_技术路线决策报告.md` 已明确，当前阶段目标是完成 v0.5.1-governance 工程治理基线；后续应基于半自动工程体系重新走一遍产品设计全流程，产品重新基线化之后，再决定下一实现版本是 v0.6 稳定演进、v0.7 产品重构，还是 v1.0 课程交付版本。v0.6 可以作为候选下一阶段之一，但不能写成唯一确定路线。`AGENTS.md` 也要求架构变更先写 ADR，不允许未经确认更换技术栈，不允许无关重构，不允许破坏 v0.5.1 已有功能。

因此，当前技术路线需要在保留当前能力、降低验收风险、补齐工程化证据和为后续产品重新基线化保留空间之间取得平衡。

## 4. 可选方案

### 方案 A：保留 Flask + Jinja2 + SQLite 单体架构，继续稳定演进

保留现有技术栈和整体架构，不做大规模结构调整，优先完成启动、测试、AI 验证、视觉验收、文档链路和必要的小范围修正。

该方案对 F001-F025 主链路影响最小，可直接服务 N001-N006、N008-N012，并为 N007、N011 是否进入实现留下后续决策空间。风险是现有结构性问题会继续存在，例如模型单文件、部分蓝图职责混合、CSS/JS 较集中。

### 方案 B：保留当前技术栈，进行局部重构

继续使用 Flask、Jinja2、SQLAlchemy 和 SQLite，但对路由边界、Service、模型拆分、CSS/JS 分层、AI Provider 抽象或事务边界做局部整理。

该方案可能改善可维护性，但需要明确需求、测试保护和 ADR。若范围失控，容易把局部重构扩大成无边界重构，反而破坏当前演示稳定性。

### 方案 C：旧架构稳定演进，同时开启新架构有限探索

主线继续稳定演进，同时另开 `arch/v1-experiment` 分支或目录，探索 API 化、前后端分离、异步 AI、搜索引擎等新方向。

该方案可以保留一定架构探索空间，但会带来双线维护、文档分叉、验证成本和答辩口径复杂度。当前缺少必须立即开启实验分支的明确需求。

### 方案 D：更换部分技术栈

例如切换数据库、引入现代前端框架、从 Flask 改为 FastAPI 或 Django，或引入任务队列、搜索引擎、前端构建体系等。

该方案可能服务远期生产化或复杂扩展需求，但当前工程治理和后续候选验证问题主要是验证、测试、AI 真实调用、视觉一致性和文档链路。换栈不能直接解决这些问题，还会引入迁移、回归和学习成本。

### 方案 E：重新开发 v1.0

以 v1.0 为目标重新开发系统，重新设计架构、模型、页面和交互。

该方案理论上可以重新承载所有需求，但会放弃当前已形成的代码、模板、脚本和追溯关系，带来极高的功能回退和工期失控风险。

## 5. 最终决策

采用方案 B 作为最终技术路线：保留当前 Flask + Jinja2 + SQLAlchemy + SQLite 技术栈，在测试保护、需求确认和 ADR 约束下做受控局部重构。

方案 B 不等于立即重写，不等于换栈，不等于前后端分离，也不等于当前 `process/unified-main-repo` 分支直接开展 v0.6 功能开发。当前 `process/unified-main-repo` 分支是工程治理分支，不是 v0.6 功能开发分支；当前阶段目标是完成 `v0.5.1-governance` 工程治理基线。

当前暂缓方案 C，不立即开启新架构探索分支；当前不采用方案 D 和方案 E，不更换技术栈，不重新开发 v1.0。

## 6. 决策理由

1. 当前 Flask + Jinja2 + SQLite 单体架构已经支撑主要业务链路，现阶段没有必须换架构才能解决的问题。
2. 当前阶段目标是完成 v0.5.1-governance 工程治理基线，后续需先重新走产品设计全流程，再决定下一实现版本。
3. 方案 B 在保留当前技术栈前提下控制调整范围，对 F001-F025 已有主业务闭环影响可控，有利于保留当前可运行、可演示的基础。
4. F026-F032 的 AI 问题主要是 API Key 配置后的真实调用验证、失败降级和记录补齐，不需要通过换栈或重写解决。
5. F033 的 AI 日志闭环需要补需求和设计，是否新增字段或流程需后续确认，不应在当前直接扩大为数据库重构。
6. F036-F050 和 N001-N012 多数属于启动验证、测试报告、错误页验收、视觉一致性、README 校准和文档链路问题，现有架构可以支撑。
7. 路线 C、D、E 都会显著增加成本和不确定性，不适合作为当前周期默认路线。
8. `AGENTS.md` 明确要求未经确认不得更换技术栈，不允许无关重构，不允许破坏 v0.5.1 已有功能。

## 7. 正面影响

1. 降低后续实现版本和课程验收的不确定性。
2. 保留当前已形成的游客、用户、作者、评论和后台治理主链路。
3. 便于继续补齐 N001-N006、N008-N012 的验证和文档闭环。
4. 避免在测试证据不足时引入数据库迁移、前端重写或后端框架迁移。
5. 有利于答辩时说明“先稳定、再演进”的工程判断。
6. 为后续 N007、N011 或 AI 日志闭环等需求保留小步调整空间。

## 8. 负面影响

1. 现有结构性问题不会在当前治理阶段被一次性解决，例如模型组织、部分蓝图职责和 CSS/JS 集中问题仍需后续观察。
2. 如果后续需求快速扩展到移动端 API、开放 API、异步 AI、全文或向量搜索、生产部署，当前单体架构可能需要重新评估。
3. SQLite 更适合课程演示和轻量使用，不能被夸大为生产级高并发数据库方案。
4. 方案 B 不等于随意重构；若启动、测试、AI 或视觉验收发现缺陷，仍需按需求、设计、测试和 Review 链路处理。
5. 暂缓重构可能让部分维护问题继续存在，后续修改时需要更谨慎地控制范围。

## 9. 后续措施

1. 先完成 N001：统一 `v0.5.1`、`V0.5`、`V5.1`、`V0.4` 的版本口径。
2. 完成 N002、N003、N004：启动初始化验收、E2E 当前测试报告、400 错误页和错误路径验收。
3. 推进 N005：对 F026-F032 做 AI 真实调用和失败降级验证。
4. 推进 N006：补 F033 AI 日志闭环需求和设计，避免把字段存在写成完整流程已实现。
5. 推进 N008、N009、N012：视觉一致性验收、README 与启动指南校准、正式文档链路补齐。
6. 若 N007 或 N011 进入实现，再评估是否需要受控局部重构、数据库变更或新的 ADR。
7. 若未来出现移动端 API、异步 AI、全文或向量搜索、生产部署等明确需求，再通过 ADR 评估新架构或技术栈替换，不能直接默认前后端分离或换栈。

## 10. 待确认事项

1. 方案 B 已作为当前 ADR 最终选择；具体局部重构范围仍需在实施前人工确认。
2. 当前 `process/unified-main-repo` 分支按工程治理分支处理，不作为 v0.6 功能开发分支。
3. 当前暂缓路线 C 的 `arch/v1-experiment` 分支探索；若未来重启，需另行 ADR。
4. 当前周期不进行路线 D 和路线 E，不更换技术栈，不重新开发 v1.0。
5. N001-N012 是否全部采纳为正式未来需求，需产品负责人或人工确认。
6. 若后续新增 `ReadingHistory`、AI 日志闭环字段或数据库结构变化，是否引入迁移方案需人工确认。
7. 若后续执行局部重构，ADR 的格式、编号、审批流程和回滚方式需人工确认。
8. 产品重新基线化之后，下一实现版本选择 v0.6、v0.7 还是 v1.0，需人工确认。
