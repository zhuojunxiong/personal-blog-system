# ADR-003 半自动工程化开发体系采用策略

## 1. 标题

采用“统一主仓库 + Agent + Skill + ADR + Git 小步提交 + 测试记录 + Review 记录 + AI 协作记录”的半自动工程化开发体系。

## 2. 状态

已采纳。

本文基于 `AGENTS.md`、`docs/04_未来需求与产品方向.md`、`docs/05_技术路线决策报告.md`、`docs/06_ADR/ADR-001-统一主仓库管理策略.md`、`docs/06_ADR/ADR-002-v0.6技术路线选择.md` 和 `docs/07_需求规格说明书.md` 形成。本文只记录工程方法决策，不修改业务代码，不更换技术栈，不安装依赖，不读取或修改 `software-practice-records`，不把未来计划写成当前已实现能力。

## 3. 背景

当前项目处于 `v0.5.1-governance` 工程治理阶段。根据 `AGENTS.md`，`personal-blog-system` 是当前统一主仓库，代码、需求、设计、测试、UML、AI 协作记录和交付材料应逐步在当前仓库中形成可追溯闭环。

`docs/07_需求规格说明书.md` 已明确，当前 `process/unified-main-repo` 分支是工程治理分支，不是 v0.6 功能开发分支。当前阶段目标不是直接扩展业务功能，而是建立统一事实源、需求规格、架构决策、测试记录、Review 记录、AI 协作记录和交付文档链路。

`docs/05_技术路线决策报告.md` 和 ADR-002 进一步确认：后续路线应保留当前 Flask + Jinja2 + SQLAlchemy + SQLite 技术栈，在测试保护、需求确认和 ADR 约束下做受控局部重构。这个前提要求后续开发不能只依赖一次性 AI 生成，也不能只依赖个人经验直接改代码，而应把需求分析、产品设计、软件设计、代码实现、测试和文档更新纳入同一套闭环。

因此，需要通过 ADR 明确后续采用半自动工程化开发体系：AI 和 Agent/Skill 作为辅助能力参与分析、生成、检查和记录，但不能替代人工确认、Git diff 检查、小步提交、测试和 Review。

## 4. 可选方案

### 方案 A：继续依赖人工手工开发和零散文档记录

由人工直接分析需求、修改代码、补文档，文档和记录按需要临时补充。

该方案流程简单，短期成本较低，但容易出现需求、设计、实现、测试和文档脱节。随着 F001-F050、N001-N012、AI 验证和后续产品重新基线化工作增多，零散记录会增加事实冲突、遗漏测试和答辩口径不一致的风险。

### 方案 B：采用半自动工程化开发体系

以 `personal-blog-system` 统一主仓库为事实源，结合 Agent 分工、Skill 机制、ADR、Git 小步提交、测试记录、Review 记录和 AI 协作记录，形成需求分析、产品设计、软件设计、代码实现、测试和文档更新的闭环。

该方案能把 AI 协作纳入可控流程，也能为后续 v0.5.1-governance、产品重新基线化和下一实现版本决策提供证据。风险是流程要求更高，短期文档和记录成本增加。

### 方案 C：高度自动化，让 AI 自动完成需求、设计、编码、测试和文档

将大部分工程活动交给 AI 自动执行，人工只做最终验收或少量干预。

该方案表面效率高，但不符合当前项目治理边界。AI 可能把未来计划写成当前实现、误读历史材料、忽略测试缺口或扩大重构范围。当前项目明确要求人工确认、事实源校验和测试记录，因此不适合作为默认工程方法。

### 方案 D：先暂停工程化体系建设，直接进入下一版本功能开发

跳过当前治理基线，直接以 v0.6、v0.7 或 v1.0 为目标推进功能。

该方案可能更快看到功能变化，但会放大版本口径、需求边界、AI 真实调用、测试证据、视觉验收和文档链路的既有缺口。它也与当前 `process/unified-main-repo` 分支的工程治理定位冲突。

## 5. 最终决策

采用方案 B：后续继续使用“统一主仓库 + Agent + Skill + ADR + Git 小步提交 + 测试记录 + Review 记录 + AI 协作记录”的半自动工程化开发体系。

具体决策如下：

1. `personal-blog-system` 继续作为统一主仓库和当前事实源。
2. Agent 和 Skill 用于辅助需求分析、架构分析、前端一致性检查、测试设计、Review 和文档整理，但不能替代人工确认。
3. 架构变更、技术路线选择、数据库结构变化、重要工程策略必须通过 ADR 记录。
4. 每轮开发必须先明确需求和变更边界，再实施代码或文档修改。
5. 每轮开发完成后必须进行 `git diff` 检查，确认只包含本轮预期变更。
6. 变更应采用 Git 小步提交，避免大范围混合提交导致无法回滚和无法 Review。
7. 涉及代码、行为、页面、AI 调用或错误路径的修改，必须补测试记录或说明未执行原因。
8. 涉及设计、重构、风险或质量判断的修改，必须补 Review 记录或明确待补齐。
9. AI 参与的需求、设计、实现、测试和文档更新，应在 AI 协作记录中沉淀关键输入、输出、人工确认和风险。
10. 需求分析、产品设计、软件设计、代码实现、测试和文档更新必须进入同一套闭环，不能只完成其中一个环节就宣称工作完成。

该决策是工程方法决策，不是技术栈变更，不改变当前 Flask + Jinja2 + SQLAlchemy + SQLite 架构，也不表示当前已经完成所有 Agent、Skill、测试报告、Review 记录或 AI 协作记录。

## 6. 决策理由

1. `AGENTS.md` 已要求统一事实源、逐步补齐文档链路、明确变更规则并建立可追溯协作流程。
2. ADR-001 已明确当前以 `personal-blog-system` 作为统一主仓库，半自动工程体系需要围绕这个事实源运行。
3. ADR-002 已确认后续采用受控局部重构路线，受控的前提就是需求、设计、ADR、测试、Review 和人工确认齐备。
4. F036-F050 和 N001-N012 多数不是单纯编码任务，而是启动、测试、错误页、AI 验证、视觉一致性、README 校准和文档链路补齐任务，需要工程闭环支撑。
5. AI 写作辅助和 AI 搜索相关能力仍存在真实调用验证、失败降级和日志闭环缺口，不能仅凭 AI 或接口存在宣称完成。
6. 半自动工程体系能提升需求、设计、实现、测试和交付材料之间的追溯性，有利于课程答辩和后续维护。
7. AI 适合作为辅助分析和生成工具，但当前项目事实必须以代码、正式文档、测试记录和人工确认为准。
8. Git 小步提交、diff 检查和 Review 记录可以降低无关重构、误删文档、破坏已有功能和无法回退的风险。

## 7. 正面影响

1. 有利于把需求、设计、实现、测试、Review、AI 协作和交付材料纳入同一事实链路。
2. 降低 AI 误生成、误归纳或扩大范围带来的工程风险。
3. 便于后续解释每个功能、文档和架构决策的来源、状态和验证证据。
4. 支撑 `v0.5.1-governance` 工程治理基线完成。
5. 为后续产品重新基线化提供稳定流程，而不是只提供零散文档。
6. 有助于保持小步提交和可回退历史，降低局部重构风险。
7. 有利于区分“已实现”“部分实现”“接口存在但需验证”“后续候选”和“需人工确认”。

## 8. 负面影响

1. 每轮开发需要额外维护需求、设计、测试、Review 或 AI 协作记录，短期效率看起来会下降。
2. 对提交粒度、文档同步和人工确认要求更高，需要持续执行才能产生价值。
3. 如果只形式化补记录而不实际验证，仍可能形成新的文档债。
4. Agent 和 Skill 的边界需要持续维护，否则可能出现职责混淆。
5. 对较小修改也需要做基本 diff 检查和记录判断，会增加一定流程成本。

## 9. 使用边界

1. 本 ADR 只定义工程方法，不定义新业务功能。
2. 本 ADR 不更换技术栈，不引入前后端分离，不引入微服务，不引入新的数据库或任务队列。
3. AI 是辅助，不是自动替代人工；AI 输出必须接受当前代码、正式文档、测试结果和人工确认校验。
4. 没有对应文件、记录或可验证证据的内容，只能写成“待建立”“后续候选”或“需人工确认”，不能写成已完成。
5. 每轮开发必须有人工确认、`git diff` 检查和小步提交；不得把多个不相关修改混在一次提交中。
6. 修改业务代码前必须先明确需求；新功能必须先写需求，再写设计，再编码。
7. 架构变更、数据库结构变化、技术栈替换、重要重构必须先写 ADR，并说明影响和回滚方式。
8. 测试记录必须基于实际执行或明确标注未执行原因，不得伪造测试通过结论。
9. Review 记录应关注行为风险、回归风险、权限边界、测试缺口和文档一致性。
10. AI 协作记录应记录关键协作过程和人工判断，不应把 AI 原始输出未经校验地当作正式事实。
11. 本 ADR 不授权读取、同步、覆盖或迁移 `software-practice-records`。

## 10. 后续措施

1. 按 `AGENTS.md` 继续补齐 `docs/09_测试报告.md`、`docs/10_代码Review记录.md`、`docs/11_AI协作记录.md` 和 `docs/12_项目总结.md`。
2. 为后续每轮需求分析、设计、实现、测试和文档更新建立统一记录模板或最小记录规范。
3. 后续若建立 `agent-prompts/` 或 `.skills/`，需先明确 Agent/Skill 职责边界，不能假设其已经存在或完成。
4. 每次代码或文档变更后执行 `git diff` 检查，并在提交前确认没有业务代码误改、无关重构或文档删除。
5. 采用小步提交保存每个可解释的治理成果，例如一个 ADR、一个需求文档、一次测试报告或一个小范围修正。
6. 涉及 F026-F032 AI 能力时，补充真实调用、无 Key、失败降级和异常返回的测试或验收记录。
7. 涉及 F033、N006、N007 或数据库结构变化时，先补需求、设计和 ADR，再判断是否实现。
8. 在产品重新基线化过程中，把需求分析、产品设计、软件设计、实现计划、测试计划和文档更新纳入同一闭环。

## 11. 待确认事项

1. Agent 和 Skill 的具体目录、命名、模板和使用方式需人工确认。
2. 每轮 AI 协作记录的最小字段、记录粒度和正式路径需人工确认。
3. 测试报告和 Review 记录是否采用单文件持续维护，还是按阶段拆分文件，需人工确认。
4. Git 小步提交的分支策略、提交信息格式和合并审批方式需人工确认。
5. 后续是否为需求、设计、测试、Review 和 AI 协作分别建立模板，需人工确认。
6. N001-N012 是否全部纳入正式后续需求，仍需产品负责人或人工确认。
7. 若后续执行局部重构，具体范围、测试保护、Review 标准和回滚方式需人工确认。
