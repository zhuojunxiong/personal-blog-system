# ADR-004 产品重新基线化策略

## 1. 标题

采用“先完成工程治理基线，再重新走产品设计全流程，最后决定下一实现版本”的产品重新基线化策略。

## 2. 状态

已采纳。

本文基于 `AGENTS.md`、`docs/04_未来需求与产品方向.md`、`docs/05_技术路线决策报告.md`、`docs/06_ADR/ADR-001-统一主仓库管理策略.md`、`docs/06_ADR/ADR-002-v0.6技术路线选择.md`、`docs/06_ADR/ADR-003-半自动工程化开发体系采用策略.md` 和 `docs/07_需求规格说明书.md` 形成。本文只记录产品规划和版本决策策略，不修改业务代码，不更换技术栈，不安装依赖，不读取或修改 `software-practice-records`，不把未来计划写成当前已实现能力。

## 3. 背景

当前项目已经从早期个人博客原型演进为“面向课程实践的多用户知识专栏博客系统”。根据 `docs/07_需求规格说明书.md`，当前系统已经形成游客浏览、用户注册登录、用户创作、评论互动和管理员后台治理的主业务闭环；AI 写作辅助和 AI 智能搜索接口已经存在，但真实 API 调用仍需验证；AI 日志闭环仍需补需求和设计；启动、测试、错误页、视觉一致性、README 和正式文档链路仍需补齐证据。

当前 `process/unified-main-repo` 分支定位为工程治理分支，目标是完成 `v0.5.1-governance` 工程治理基线。它不是 v0.6 功能开发分支，也不应直接承诺下一阶段必然进入 v0.6。

`docs/04_未来需求与产品方向.md` 和 `docs/05_技术路线决策报告.md` 已明确：后续应基于半自动工程体系重新走一遍产品设计全流程，产品重新基线化之后，再决定下一实现版本是 v0.6 稳定演进、v0.7 产品重构，还是 v1.0 课程交付版本。

ADR-002 已选择方案 B：保留当前技术栈，在测试保护、需求确认和 ADR 约束下做受控局部重构。因此，产品重新基线化不是推翻当前系统，也不是立即重写，而是在保留当前主链路和事实源的前提下，重新确认产品定位、角色、需求、优先级、版本目标、验收标准和实施边界。

## 4. 可选方案

### 方案 A：当前治理基线完成后直接锁定 v0.6 稳定演进

完成当前文档治理后，直接将下一阶段定义为 v0.6，并默认推进 N001-N012 中的候选验证和局部修正。

该方案路径清晰，适合快速进入稳定演进，但会过早锁定版本目标。当前 N001-N012 是否全部采纳、AI 日志闭环是否进入实现、真实最近阅读是否需要新增模型、视觉问题是否需要改动，都仍需产品负责人或人工确认。

### 方案 B：先完成工程治理基线，再重新走产品设计全流程，之后决定下一实现版本

当前分支先完成 `v0.5.1-governance` 工程治理基线。之后基于统一主仓库、Agent、Skill、ADR、Git 小步提交、测试记录、Review 记录和 AI 协作记录，重新梳理产品定位、用户角色、需求池、优先级、验收标准和版本目标。产品重新基线化之后，再决定下一实现版本是 v0.6 稳定演进、v0.7 产品重构，还是 v1.0 课程交付版本。

该方案最符合当前文档口径，能保留 v0.6、v0.7 和 v1.0 的选择空间。风险是短期不会直接进入功能开发，需要先完成产品设计和确认流程。

### 方案 C：直接进入 v0.7 产品重构

将下一阶段定义为产品重构，围绕页面体验、产品结构、模块边界和局部业务流程做较大调整。

该方案可能改善产品体验和结构，但当前测试、AI 真实调用、视觉验收和文档闭环证据仍不足。若未先完成治理基线和产品重新基线化，直接重构容易扩大范围，破坏当前已形成的演示能力。

### 方案 D：直接进入 v1.0 课程交付版本

将下一阶段直接定义为 v1.0，集中整理课程交付材料并补齐必要演示路径。

该方案目标明确，适合课程交付压力较高时采用。但当前仍需先确认 v1.0 到底是“稳定交付包”还是“重写后的完整版”。如果不先重新基线化，容易把 v1.0 误解为必须重写或必须扩展大量功能。

### 方案 E：推翻当前系统并重新开发

以新的产品定义和架构重新开发系统，重新设计模型、页面、交互和技术方案。

该方案理论上可以重新整理所有问题，但会放弃当前已经形成的代码、模板、脚本和追溯关系，带来极高的功能回退、测试不足和工期失控风险。它也与 ADR-002 的受控局部重构路线冲突。

## 5. 最终决策

采用方案 B：当前 `process/unified-main-repo` 分支先完成 `v0.5.1-governance` 工程治理基线；后续不直接锁定 v0.6；后续先基于半自动工程化开发体系重新走一遍产品设计全流程；产品重新基线化之后，再决定下一实现版本是 v0.6 稳定演进、v0.7 产品重构，还是 v1.0 课程交付版本。

具体决策如下：

1. 当前 `process/unified-main-repo` 分支按工程治理分支处理，不作为 v0.6 功能开发分支。
2. 当前优先完成统一主仓库、正式文档、ADR、需求规格、测试记录、Review 记录、AI 协作记录和项目总结等治理基线。
3. 后续不直接锁定 v0.6，也不把 v0.6 写成唯一确定路线。
4. 后续先重新走产品设计全流程，包括产品定位、用户角色、场景、需求池、优先级、范围取舍、验收标准、版本目标和风险确认。
5. 产品重新基线化之后，再在 v0.6 稳定演进、v0.7 产品重构、v1.0 课程交付版本之间做下一实现版本选择。
6. 该策略不等于推翻当前系统，不等于立即重写，也不等于更换技术栈。
7. 若后续进入 ADR-002 方案 B 的局部重构，必须有测试保护、需求确认和 ADR。

## 6. 决策理由

1. 当前系统已经形成 F001-F025 主业务闭环，后续版本应优先保留而不是推翻。
2. 当前主要缺口集中在 F026-F033 的 AI 验证和日志闭环，以及 F036-F050 的启动、测试、错误页、视觉、README 和文档链路证据，不需要通过立即重写解决。
3. N001-N012 目前是后续候选需求，是否全部采纳为正式需求仍需人工确认。
4. 直接锁定 v0.6 会过早固化路线，可能掩盖 v0.7 产品重构或 v1.0 课程交付的真实优先级。
5. 直接进入 v0.7 或 v1.0 也可能绕过当前工程治理基线，使需求、设计、测试和文档继续断链。
6. 产品重新基线化可以把当前事实、后续候选、课程交付目标和实现成本重新放到同一个决策框架里。
7. ADR-002 已明确当前不更换技术栈、不前后端分离、不重新开发 v1.0，后续局部重构必须受测试、需求和 ADR 约束。
8. ADR-003 提供了半自动工程体系，可以支撑重新走产品设计全流程并保留人工确认和可追溯记录。

## 7. 正面影响

1. 避免在治理基线未完成时过早承诺 v0.6、v0.7 或 v1.0。
2. 保留当前已形成的游客、用户、作者、评论和后台治理主链路。
3. 让下一实现版本选择建立在需求、设计、测试、Review 和 AI 协作记录之上。
4. 有利于区分当前已实现能力、部分实现能力、接口存在但需验证能力和后续候选需求。
5. 降低把未来计划写成当前已实现成果的风险。
6. 为 AI 日志闭环、真实最近阅读、搜索体验增强和视觉一致性等候选需求保留人工决策空间。
7. 有利于课程答辩时说明“先治理、再基线化、再选择版本”的工程判断。

## 8. 负面影响

1. 下一实现版本不会在当前 ADR 中直接确定，短期路线看起来不如直接锁定 v0.6 明确。
2. 产品重新基线化需要额外时间重新梳理产品定位、需求、优先级和验收标准。
3. 若人工确认长期缺失，N001-N012 和下一版本选择可能继续悬置。
4. 工程治理和产品重新基线化之间需要保持文档一致，否则可能形成新的版本口径冲突。
5. 对希望快速新增功能的开发节奏来说，该策略会增加前置确认成本。

## 9. 使用边界

1. 本 ADR 只定义产品重新基线化和版本选择策略，不直接新增业务功能。
2. 当前 `process/unified-main-repo` 分支只用于完成工程治理基线，不作为 v0.6 功能开发分支。
3. 后续不直接锁定 v0.6；v0.6 只是产品重新基线化后的候选下一实现版本之一。
4. 产品重新基线化不等于推翻当前系统，不等于立即重写，不等于前后端分离，不等于更换技术栈。
5. 当前已形成的 F001-F025 主业务闭环应作为后续版本的保留能力，不应在缺少测试保护时破坏。
6. F026-F032 只能写成代码接口存在且真实 API 调用需验证，不能写成真实调用已通过。
7. F033 只能写成基础日志存在且闭环需完善，不能写成采纳闭环已完成。
8. N001-N012 是后续候选需求，进入实现前必须经过产品重新基线化和人工确认。
9. 若进入方案 B 的局部重构，必须先明确需求、补设计、补测试保护，并通过 ADR 记录影响和回滚方式。
10. 若未来确需移动端 API、开放 API、异步 AI、全文或向量搜索、生产部署、技术栈替换或大规模重写，必须另行 ADR。
11. 本 ADR 不授权读取、同步、覆盖或迁移 `software-practice-records`。

## 10. 后续措施

1. 先完成 `v0.5.1-governance` 工程治理基线，补齐正式文档链路。
2. 完成 N001：统一 `v0.5.1`、`V0.5`、`V5.1`、`V0.4` 的版本口径。
3. 完成 N002、N003、N004：启动初始化验收、当前 E2E 测试报告、400 错误页和错误路径验收。
4. 推进 N005：对 F026-F032 做 AI 真实调用、无 Key、失败降级、超时和异常返回验证。
5. 推进 N006：补 F033 AI 日志闭环需求和设计，避免把字段存在写成完整流程已实现。
6. 推进 N008、N009、N012：视觉一致性验收、README 与启动指南校准、正式文档链路补齐。
7. 在治理基线完成后，基于 ADR-003 的半自动工程体系重新走产品设计全流程。
8. 产品重新基线化时，重新确认产品定位、用户角色、核心场景、需求池、优先级、验收标准、版本目标和暂缓范围。
9. 产品重新基线化之后，再通过 ADR 或版本规划文档确认下一实现版本是 v0.6、v0.7 还是 v1.0。
10. 若下一版本需要局部重构，按 ADR-002 方案 B 执行：测试保护、需求确认、ADR、Review 和小步提交缺一不可。

## 11. 待确认事项

1. `v0.5.1-governance` 工程治理基线的完成标准需人工确认。
2. 产品重新基线化的参与角色、评审方式和输出文档需人工确认。
3. N001-N012 是否全部采纳为正式后续需求，需产品负责人或人工确认。
4. 下一实现版本选择 v0.6 稳定演进、v0.7 产品重构还是 v1.0 课程交付版本，需在产品重新基线化后人工确认。
5. 若选择 v0.6，具体纳入哪些启动、测试、AI、视觉、README 和文档任务需人工确认。
6. 若选择 v0.7，产品重构范围、页面调整范围、测试保护和回滚方式需人工确认。
7. 若选择 v1.0，课程交付标准、演示路径、测试证据和交付材料清单需人工确认。
8. 若后续新增 `ReadingHistory`、AI 日志闭环字段或其他数据库结构变化，是否引入迁移方案需人工确认。
9. 若后续执行局部重构，ADR 的编号、审批流程、Review 标准和回滚方式需人工确认。
10. 当前周期继续禁止技术栈替换、前后端分离、大规模重写和无关重构，除非未来另行确认并形成新的 ADR。
