## 1. 文档目的

本文档用于沉淀 `personal-blog-system` 在 v0.5.1 阶段的正式需求规格，明确系统目标、用户角色、功能范围、非功能约束、数据需求、权限边界、AI 辅助能力、管理后台能力、测试验收要求和后续版本范围。

本文档服务以下目标：

1. 作为 v0.5.1-governance 工程治理基线、后续产品重新设计、测试、Review 和交付材料的需求依据。
2. 将 F001-F050 从需求追溯结果整理为可验收、可追踪的正式规格。
3. 区分当前已实现能力、部分实现能力、接口存在但未验收能力、后续候选需求和暂缓范围。
4. 为后续产品重新基线化和下一实现版本决策提供需求边界。
5. 避免把历史文档、外部目录、后续计划或 AI 输出误写成当前事实。

本文档不是概要设计说明书，不定义新的架构方案；不是测试报告，不声明未执行过的测试结果；不是开发任务清单，不直接要求修改业务代码。

## 2. 项目背景

当前项目在 v0.5.1 治理基础上，已重新收束为面向知识创作者和学习者的 AI 驱动知识写作与搜索平台。系统保留多用户写作、互动、知识合集和后台治理能力，但产品主线从“栏目浏览”调整为“自然语言搜索 + Markdown 写作 + 发布后 AI 搜索摘要 + 阅读互动”的知识闭环。

根据 `AGENTS.md`，当前阶段为 v0.5.1，定位是统一主仓库和工程化治理阶段，重点是统一事实源、补齐文档链路、明确变更规则、建立可追溯的协作流程。

根据 ADR-001，当前以 `personal-blog-system` 作为统一主仓库，`software-practice-records` 不作为当前事实源，不自动读取、同步、覆盖或迁移。

当前 `process/unified-main-repo` 分支是工程治理分支，不是 v0.6 功能开发分支。本分支目标是建立 `v0.5.1-governance` 工程治理基线，包括统一主仓库、Agent 分工、Skill 机制、ADR、Git 小步提交、测试记录、Review 记录、AI 协作记录和交付文档链路。

后续路线不应简单表述为“v0.5.1 之后直接进入某个固定功能版本”。更准确的路线是：当前先完成 `v0.5.1-governance` 工程治理基线；然后基于这套体系重新走一遍产品设计全流程；产品重新基线化之后，再决定下一实现版本是 v0.6 稳定演进、v0.7 产品重构，还是 v1.0 课程交付版本。

本文按 ADR-002 选择方案 B 记录：保留当前 Flask + Jinja2 + SQLite 技术栈，在测试保护、需求确认和 ADR 约束下做受控局部重构。方案 B 不等于立即重写，不等于换栈，不等于前后端分离，也不等于当前分支直接开展功能开发。

## 5. 业务目标

系统业务目标如下：

1. 为课程实践提供一个可运行、可演示、可追溯的多用户知识专栏博客系统。
2. 支撑游客侧内容消费闭环：浏览、阅读、分类、标签、专栏、作者主页和搜索。
3. 支撑普通用户侧创作闭环：注册登录、资料维护、专栏创建、文章写作、草稿保存、文章发布和自主管理。
4. 支撑互动闭环：评论、审核、点赞、收藏。
5. 支撑管理员基础治理闭环：用户、文章、专栏、分类、标签、评论和 AI 状态管理。
6. 在不替代主业务闭环的前提下，提供 AI 写作辅助和 AI 搜索增强接口。
7. 在当前 `v0.5.1-governance` 阶段优先建立统一主仓库、Agent、Skill、ADR、Git 小步提交、测试记录、Review 记录、AI 协作记录和正式文档链路。
8. 在治理基线完成后，基于这套体系重新走一遍产品设计全流程，再决定下一实现版本是 v0.6 稳定演进、v0.7 产品重构，还是 v1.0 课程交付版本。

## 10. AI 辅助功能需求

AI 辅助功能当前必须按三层状态表述：

1. 接口存在：代码层面存在路由、服务封装或前端入口。
2. 真实 API 调用需验证：需要配置 API Key 后实际调用远程服务，验证成功、失败、超时和异常返回。
3. 日志闭环需完善：不仅记录调用，还应明确 AI 输出是否被采用、采用结果和问题标记等流程。

## 阶段性结论

当前正式需求规格应以 F001-F050 为主线：保留已形成的游客浏览、用户创作、互动和后台治理闭环；对 F026-F032 AI 能力只确认接口存在并要求真实调用验证；对 F033 明确日志闭环需完善；对 F036-F050 明确启动、测试、错误页、视觉、文档和工程治理仍需补齐证据。

N001-N012 可作为工程治理基线之后的候选验证需求池，但不能写成当前已实现。当前最稳妥的路线不是直接承诺进入 v0.6，而是先完成 `v0.5.1-governance` 工程治理基线，再基于统一主仓库、Agent、Skill、ADR、Git 小步提交、测试记录、Review 记录和 AI 协作记录等体系重新走一遍产品设计全流程。产品重新基线化之后，再决定下一实现版本是 v0.6 稳定演进、v0.7 产品重构，还是 v1.0 课程交付版本。
