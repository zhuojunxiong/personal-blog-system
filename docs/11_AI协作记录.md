## 5. Git commit 如何保存证据

当前半自动工程体系要求通过 Git 小步提交保存证据。建议每一轮协作结束后按以下方式保留证据：

```bash
git status --short --branch
git diff -- docs/10_代码Review记录.md docs/11_AI协作记录.md
git add docs/10_代码Review记录.md docs/11_AI协作记录.md
git commit -m "docs: add review and AI collaboration records"
```

证据保存要点：

| 证据类型 | 建议保存方式 |
|---|---|
| 分支定位 | `git status --short --branch` 显示当前位于 `process/unified-main-repo`。 |
| 修改范围 | `git diff -- docs/10_代码Review记录.md docs/11_AI协作记录.md` 确认只改工程记录。 |
| 记录正文 | 通过 Git commit 保存 Review 记录和 AI 协作记录。 |
| 人工确认 | 提交前由人工确认是否接受文档口径和待确认事项。 |
| 后续测试 | 测试执行后另行提交测试报告，不与本轮记录混合。 |

注意：Git commit 只能保存“本轮文档变更证据”，不能替代测试通过、AI 真实调用通过或人工最终验收。

### 11.2 关键发现与修复

#### T002 数据库表丢失

**现象**：浏览器搜索时抛出 `sqlite3.OperationalError: no such table: articles`。

**根因**：`git restore .` 回退代码后，`instance/personal_blog.sqlite` 文件虽存在（368KB），但 `sqlite_master` 查询返回空——所有表均不存在。代码中 `ensure_sqlite_schema()` 的 ALTER TABLE 逻辑依赖表已存在的前提，无法处理完全空库的情况。

**修复**：
```bash
.venv/bin/python scripts/init_db.py --reset   # 重建所有表
.venv/bin/python scripts/demo_data.py          # 写入演示数据
```

**教训**：git restore 不保证数据库文件和代码模型同步。如果数据库是在 restore 之前的旧模型创建的，restore 后可能出现字段缺失；如果 restore 到一个数据库文件被清空的版本，则需完全重建。

#### T004 DeepSeek API 优化细节

优化前各场景 max_tokens 保守（800-3000），未充分利用 DeepSeek-V3 的 8K 输出能力。优化后：

| 场景 | 优化前 | 优化后 | 提升幅度 |
|------|--------|--------|----------|
| polish（润色） | 3000 | 4096 | +37% |
| research（资料整理） | 2200 | 4096 | +86% |
| search_summary（搜索摘要） | 1600 | 3000 | +88% |
| search_rerank（搜索重排） | 2000 | 3000 | +50% |
| chat（问答） | 2000 | 3000 | +50% |
| outline（大纲） | 2000 | 3000 | +50% |
| summary（摘要） | 1500 | 2000 | +33% |
| search_intent（搜索意图） | 800 | 1200 | +50% |
| tags（标签） | 800 | 1200 | +50% |
| title（标题） | 800 | 1200 | +50% |

全局配置：`AI_TIMEOUT` 30→60s，`AI_MAX_TOKENS` 2000→4096。
