## 1. 项目背景

`personal-blog-system`（又名 `zjx`）是一个面向课程实践的多用户知识专栏博客系统。项目采用 Flask + Jinja2 + SQLAlchemy + SQLite 技术栈，以服务端渲染单体应用形态运行。

项目经历了以下演进阶段：

| 阶段 | 内容 | 文档依据 |
|---|---|---|
| v0.1–v0.4 | 需求驱动快速原型开发。从项目骨架搭建、基础业务闭环、多用户平台到前端与交互重构。 | `archive/old_docs/day1-development-record.md` 至 `archive/old_docs/day4-development-record.md`、`archive/old_docs/v0.4.1-design-note.md`、`archive/old_docs/v0.4.1-implementation-rules.md`（已归档至 archive/old_docs/） |
| v0.5 | 真实 AI 接入、安全加固、写作体验升级。 | `archive/old_docs/v0.5-release-notes.md`、`archive/old_docs/v5.1-release-notes.md`（已归档至 archive/old_docs/） |
| v0.5.1-governance | **工程治理阶段**。从”需求驱动快速原型开发”转向”工程治理与可追溯开发”。重点不是扩展业务功能，而是统一事实源、补齐文档链路、明确变更规则、建立可追溯的协作流程。 | `AGENTS.md`、全部正式文档 |
| v1.0 | **课程交付阶段**。在 v0.5.1-governance 治理基线之上，完成系统理解、启动验证、AI 配置优化、教师资料项目化纳入和最终交付准备。目标是将项目收束为”AI 驱动的知识写作与搜索平台”，形成可演示、可追溯、可答辩的课程交付包。 | CR-002、CR-003、CR-009、ADR-005、system-understanding 文档 |

项目在 v0.5.1-governance 之前的特点：功能迭代快，但需求、设计、实现、测试和文档之间存在缺口；版本命名不一致（`v0.5.1`、`V0.5`、`V5.1` 并存）；历史文档中的“已完成”与当前代码实际状态未经过系统核对。

## 2. 当前分支目标

当前分支 `work/v1.0-course-delivery` 是 v1.0 课程交付分支。v0.5.1-governance 阶段已在 `process/unified-main-repo` 分支完成 **v0.5.1-governance 工程治理基线**，包括：

1. 以 `personal-blog-system` 为统一主仓库，`software-practice-records` 不作为当前事实源。
2. 补齐从需求追溯、架构追溯、技术路线决策、ADR、需求规格、概要设计到测试报告、代码 Review、AI 协作记录和项目总结的完整文档链路。
3. 统一版本口径，明确 `v0.5.1`、`V0.5`、`V5.1`、`V0.4` 的关系。
4. 建立半自动工程化开发体系（Agent + Skill + ADR + Git 小步提交 + 测试记录 + Review 记录 + AI 协作记录）。
5. 通过 ADR 明确统一主仓库策略（ADR-001）、技术路线选择（ADR-002）、半自动工程体系（ADR-003）和产品重新基线化策略（ADR-004）。
6. 为后续选择下一实现版本（v0.6 / v0.7 / v1.0）留下决策空间。

在此基础上，当前 v1.0 课程交付分支的目标是：完成系统理解、启动验证、AI 配置优化、教师资料项目化纳入，将项目收束为"AI 驱动的知识写作与搜索平台"，形成可演示、可追溯、可答辩的课程交付包。

## 3. v0.5.1-governance 阶段目标

v0.5.1-governance 是项目从“能跑就行”转向“工程可追溯”的关键阶段。核心目标：

1. **统一事实源**：以当前代码为最高优先级事实，`docs/` 正式文档为第二优先级，外部 `software-practice-records` 不作为当前事实源。
2. **补齐文档链路**：按 `AGENTS.md` 规划的路径，从 `archive/old_docs/00_docs_inventory.md`（已归档至 archive/old_docs/）到 `docs/12_项目总结.md` 逐步建立正式文档。
3. **建立追溯闭环**：需求（F001–F050）→ 架构 → 设计 → 测试计划 → Review → AI 协作记录 → 项目总结，形成可追溯链条。
4. **明确变更规则**：新功能先写需求再写设计再编码；架构变更先写 ADR；不允许无关重构；不允许未经确认更换技术栈。
5. **建立半自动工程体系**：明确 Agent 分工、Skill 机制、ADR 流程、Git 小步提交和人工确认边界。
6. **为产品重新基线化做准备**：在治理基线完成后，基于半自动工程体系重新走产品设计全流程，再决定下一实现版本。

## 9. 半自动工程化体系说明

本阶段建立并实践了半自动工程化开发体系，定义为：

> 统一主仓库 + Agent + Skill + ADR + Git 小步提交 + 测试记录 + Review 记录 + AI 协作记录

**核心原则：**

1. AI 是辅助工具，不是自动完成全部项目的“自动驾驶”。
2. 每个阶段需要人工确认输入范围、输出口径和禁止事项。
3. Agent 有明确角色边界（requirement 不写代码，architect 不新增需求，tester 不修改代码，reviewer 不直接重构）。
4. 架构变更、技术路线、工程策略必须通过 ADR 记录。
5. 每次变更必须通过 Git 小步提交保存证据，`git diff` 检查确保无误改。
6. 测试记录必须基于实际执行或明确标注未执行原因，不得伪造。
7. AI 协作记录应记录关键约束、输出和人工确认。

**本阶段的实践效果：**

- 全部 13 份正式文档均按 Agent 角色边界生成（requirement Agent 产出需求追溯和需求规格，architect Agent 产出架构追溯和概要设计等）。
- 每份文档开头均声明角色边界、输入范围、禁止事项。
- 所有不确定内容均标注“需人工确认”。
- 通过 15 次小步提交保存了治理过程的完整证据。

## 10. 方案 B 技术路线说明

经 `docs/05_技术路线决策报告.md` 五条路线对比评估，ADR-002 最终采纳方案 B：

> 保留当前 Flask + Jinja2 + SQLAlchemy + SQLite 技术栈，在测试保护、需求确认和 ADR 约束下做受控局部重构。

**方案 B 的含义：**

- ✅ 保留现有技术栈和主业务闭环（F001–F025）。
- ✅ 可以在测试保护下做局部重构（路由边界、Service 收敛、CSS/JS 分层等）。
- ✅ 架构变更前必须写 ADR。
- ❌ 不等于立即重写。
- ❌ 不等于更换技术栈（不换 Flask、不换 Jinja2、不换 SQLite）。
- ❌ 不等于前后端分离。
- ❌ 不等于当前分支直接开展 v0.6 功能开发。

**方案 B 的边界：**

局部重构只能由明确需求或缺陷触发，必须满足：明确需求或问题触发 → 补测试保护 → 涉及架构边界时补 ADR → 不把局部重构成伪装成产品需求。

## 13. 后续可能版本路线

后续版本路线尚未确定，以下是候选方向（按 ADR-004，需在产品重新基线化后决策）：

### 候选一：v0.6 稳定演进

- **定位**：在当前主业务闭环基础上优先补齐验证和文档证据。
- **可能纳入**：N001–N006、N008–N009、N012（版本口径、启动验证、E2E 测试报告、400 错误页验收、AI 真实调用验证、AI 日志闭环设计、视觉验收、README 校准、文档链路补齐）。
- **不适合纳入**：大规模重构、技术栈替换、新业务域。
- **优势**：风险最低，与当前治理基线衔接最紧密。
- **劣势**：结构性问题（U010–U014）不会一次性解决。

### 候选二：v0.7 产品重构

- **定位**：在重新产品设计后，对产品结构、页面体验或局部业务边界做受控调整。
- **可能纳入**：在 v0.6 基础上，对路由边界、Service 收敛、CSS/JS 分层、模板体系做受控整理。
- **前置条件**：必须先完成 v0.6 的验证和测试保护。
- **优势**：可以系统性改善产品体验和维护性。
- **劣势**：范围容易失控；必须先有测试保护和 ADR。

### 候选三：v1.0 课程交付版本

- **定位**：形成可演示、可追溯、可答辩的课程交付包。
- **可能纳入**：需求、设计、实现、测试、Review、AI 协作、总结全部可追溯；演示路径稳定；AI 能力有可验证证据或明确的未实现说明。
- **前置条件**：治理基线完成 + 产品重新基线化完成 + 至少完成 v0.6 级验证。
- **优势**：目标明确，适合课程答辩。
- **劣势**：不应被误解为“必须重写”或“必须包含所有远期功能”。

### 当前明确不走的路线

- 不直接锁定 v0.6 为唯一下一版本。
- 不更换技术栈（Flask、Jinja2、SQLite）。
- 不前后端分离。
- 不重新开发 v1.0。
- 不开启新架构实验分支（除非有明确需求和 ADR）。
