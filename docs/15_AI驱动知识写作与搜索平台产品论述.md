## 1. 项目一句话定位

本项目“稷下”是一个面向知识创作者和学习者的 **AI 驱动知识写作与搜索平台**。

它不是传统意义上以栏目导航为中心的博客系统，也不是只提供问答或搜索框的单点 AI 工具。它的核心目标是解决一个更完整的问题：

> 知识被写出来之后，怎样被真正需要它的人准确找到？

因此，本项目的主线不是“有多少分类、标签、专栏”，而是围绕知识生命周期形成闭环：

```text
作者写作
  -> AI 辅助创作
  -> 发布时 AI 总结文章特征
  -> 摘要进入搜索系统
  -> 读者用自然语言搜索
  -> AI 匹配最相关文章
  -> 读者阅读、点赞、收藏、评论
  -> 互动反馈反映内容价值
  -> 作者继续优化文章和知识主页
```

这个闭环把写作者、阅读者、文章、搜索、AI 和互动数据连在一起，使系统从“能发文章”进一步变成“能让知识被发现、被理解、被反馈”的知识平台。

## 2. 为什么不再定位为传统多用户博客

项目早期从个人博客演进为多用户知识专栏博客系统，这一阶段已经建立了很多必要基础：

1. 用户注册、登录和权限体系。
2. 文章发布、编辑、删除和草稿能力。
3. 评论、点赞、收藏等互动能力。
4. 分类、标签、专栏等内容组织能力。
5. 管理员后台治理能力。
6. AI 写作辅助和 AI 搜索接口雏形。

这些能力仍然重要，但如果继续把产品表达为“多用户知识专栏博客系统”，系统主线会变得过宽：

- 读者可能以为需要先理解分类、标签、专栏才能找到内容。
- 作者可能把重点放在填栏目、选标签，而不是写出可被理解的知识。
- AI 功能容易变成页面旁边的附属按钮，而不是知识闭环的关键环节。
- 项目展示时容易变成“功能清单很多”，但不够说明“这个系统真正解决什么问题”。

因此，本项目的产品基线需要收束为“AI 驱动知识写作与搜索平台”。这并不是推翻原系统，而是对原有能力重新排序：

| 原有能力 | 新定位 |
| --- | --- |
| 首页、发现页 | 首页以自然语言搜索为主，发现页作为补充 |
| 分类 | 后台治理和管理字段，前台弱化 |
| 标签 | 搜索辅助字段，不让用户承担过多标签维护成本 |
| 专栏 | 作者知识合集，用于组织个人长期主题 |
| 传统搜索 | AI 搜索失败时的稳定降级基础 |
| AI 写作 | 服务写作质量和搜索摘要生成 |
| AI 搜索 | 前台内容发现主入口 |

这种调整使项目主线更清晰，也更适合课程答辩：系统不是简单堆功能，而是在解决“知识创作到知识发现”的完整问题。

## 3. 用户角色与核心诉求

### 3.1 阅读者

阅读者的目标不是浏览栏目，而是解决问题。

典型场景包括：

1. 想学习某个技术点，例如“我想学 Flask 登录权限怎么做”。
2. 想参考项目经验，例如“有没有数据库设计的课程项目经验”。
3. 想准备课程答辩，例如“怎么把软件实践项目整理成答辩材料”。
4. 想找到某位作者的知识体系，例如查看作者的 Markdown 主页和知识合集。

阅读者的核心诉求是：

- 不需要知道文章标题。
- 不需要先选择分类。
- 可以用自然语言描述问题。
- 搜索结果要解释为什么推荐。
- 进入文章后可以快速判断文章是否有帮助。
- 可以通过点赞、收藏、评论表达反馈。

### 3.2 写作者

写作者的目标是沉淀知识，并让知识被找到。

典型场景包括：

1. 把课程项目经验整理成文章。
2. 把学习笔记整理成 Markdown 文档。
3. 用 AI 查找资料，避免从空白开始写。
4. 让 AI 帮忙列大纲、润色表达。
5. 发布文章时自动生成搜索摘要，让后续读者更容易搜到。
6. 用 Markdown 个人主页展示研究方向、代表文章、学习路线和项目经历。

写作者的核心诉求是：

- 写作界面安静、清晰，不被过多栏目打断。
- AI 助手实用，而不是功能按钮堆砌。
- 写完文章后系统自动整理文章特征。
- 文章能够进入搜索系统，被真实需要的人找到。
- 个人主页能体现自己的知识方向。

### 3.3 管理员

管理员的目标是保证平台可治理、可演示、可维护。

管理员需要：

- 管理用户状态。
- 管理文章内容。
- 管理评论审核。
- 管理分类、标签、知识合集等基础数据。
- 查看 AI 接口配置状态。
- 保持课程项目演示数据和后台治理链路完整。

管理员不是内容生产主角，但管理员能力保证系统不是一个无治理的写作玩具，而是一个具备基础平台管理能力的 Web 系统。

## 4. 核心产品闭环

### 4.1 写作入口

作者登录后进入写作工作台。

写作工作台的核心是 Markdown 写作，而不是复杂表单。页面应保持左右分栏：

- 左侧：标题、摘要、Markdown 正文、发布设置。
- 右侧：AI 写作助手。

写作页仍保留后台分类、搜索辅助标签、知识合集等字段，但这些字段不应该喧宾夺主。它们服务于系统治理和内容组织，不是写作体验的中心。

### 4.2 AI 辅助创作

AI 助手只保留四项核心能力：

| 功能 | 目的 | 说明 |
| --- | --- | --- |
| 搜资料 | 帮作者补充写作素材 | 根据主题搜索网页资料，由 AI 整理成要点和来源 |
| 整理大纲 | 帮作者组织结构 | 根据主题或正文生成文章骨架 |
| 润色正文 | 提升表达质量 | 修正语病、优化逻辑和表达，但保留作者风格 |
| 搜索摘要 | 连接写作和搜索 | 生成用于搜索系统理解文章的摘要 |

项目刻意不把 AI 助手扩展成过多按钮。例如“判断适合人群”“单独提炼关键词”“重新整理成搜索结构”都不作为独立功能。它们可以隐含在搜索摘要中完成，但不应该成为写作页上的独立入口。

这样做的原因是：AI 助手越多越不一定越好。对于本项目而言，AI 的职责应该聚焦：

1. 帮作者更顺利地写。
2. 帮文章更准确地被搜到。

### 4.3 发布后搜索摘要

文章发布时，系统自动生成搜索用 AI 摘要。

这一步是项目闭环的关键，因为它把“写文章”和“被搜索到”连接起来。

搜索摘要不同于普通文章简介：

- 普通简介主要给读者浏览页面时看。
- 搜索摘要主要给搜索系统理解文章时用。

搜索摘要应包括：

1. 核心主题：文章主要讲什么。
2. 解决的问题：文章能帮助读者解决哪些具体困惑。
3. 关键知识点：文章涉及哪些重要概念或实践经验。
4. 可能的搜索问题：读者可能用什么自然语言搜到它。
5. 相关术语：帮助召回的相关表达。
6. 推荐理由：为什么这篇文章值得被推荐。

当前实现中，文章模型保存 `ai_search_summary` 和 `ai_search_generated_at`。发布文章时系统会尝试调用 AI 生成搜索摘要；如果未配置 AI Key 或调用失败，则使用本地降级摘要，保证发布流程不被外部服务阻断。

### 4.4 自然语言搜索

阅读者进入 `/home`，看到的是极简搜索界面。

用户不需要先选择分类，也不需要知道文章标题，而是可以直接输入问题。例如：

```text
我想学 Flask 登录权限怎么做
有没有关于数据库设计的项目经验
怎么把课程项目整理成答辩材料
```

系统搜索流程可以分为三层：

1. 基础召回：从标题、人工摘要、AI 搜索摘要、正文、作者、标签等字段中找候选文章。
2. AI 理解：理解用户搜索意图，扩展相关表达。
3. AI 重排：对候选文章排序，并生成推荐理由。

搜索结果应该像知识推荐，而不是普通文章列表。它至少需要展示：

- 文章标题。
- 搜索摘要。
- 推荐理由。
- 作者。
- 相关性说明。
- 互动数据。

AI 搜索失败时，系统不能瘫痪。传统关键词搜索必须作为降级路径保留。这也是本项目不立即引入复杂向量数据库的原因：当前阶段先保证课程项目可运行、可演示、可解释，再逐步增强搜索质量。

### 4.5 阅读与互动

读者进入文章页后，页面应保持简洁。

文章页主要承担四件事：

1. 展示 Markdown 渲染正文。
2. 展示搜索摘要或文章导读。
3. 展示作者入口和知识合集信息。
4. 提供点赞、收藏、评论等轻互动。

点赞表示“这篇文章有帮助”。

收藏表示“以后还想看”。

评论表示“我想补充、提问或交流”。

互动数据不是复杂社区系统，也不是热榜算法的基础承诺。它在当前阶段主要用于表达文章价值，并为未来可能的排序优化保留空间。

### 4.6 作者知识主页

每个作者都有公开个人主页。

个人主页不是普通资料卡，而是作者的知识名片。它支持 Markdown 内容，适合展示：

- 作者简介。
- 研究方向。
- 代表文章。
- 学习路线。
- 项目经历。
- 知识地图。
- 专题或知识合集。

这样，读者通过搜索找到一篇文章后，如果认可作者，可以进入作者主页继续了解其知识体系。

## 5. 功能体系

### 5.1 前台功能

前台功能以搜索和阅读为中心。

| 功能 | 说明 |
| --- | --- |
| 首次进入页 `/` | 用于第一次进入系统时的品牌入口 |
| 搜索首页 `/home` | 后续主首页，提供自然语言搜索 |
| 搜索结果页 | 展示 AI 理解、推荐理由和文章摘要 |
| 文章阅读页 | 展示 Markdown 正文、搜索摘要、作者和互动 |
| 作者主页 | 展示作者 Markdown 知识主页、文章和知识合集 |
| 文章列表/发现页 | 作为补充浏览入口，不作为产品主入口 |

### 5.2 写作者功能

写作者功能以 Markdown 写作和 AI 助手为中心。

| 功能 | 说明 |
| --- | --- |
| 注册登录 | 获得创作和互动权限 |
| 写文章 | 编辑标题、摘要、Markdown 正文和发布设置 |
| 保存草稿 | 未完成文章可暂存 |
| 发布文章 | 发布后自动生成搜索摘要 |
| 编辑文章 | 作者可继续修改自己的文章 |
| 删除文章 | 作者可删除自己的文章 |
| 管理知识合集 | 将文章组织为作者自己的长期专题 |
| 编辑知识主页 | 用 Markdown 维护公开个人主页 |

### 5.3 AI 功能

AI 功能分为写作侧和搜索侧。

写作侧：

1. 搜资料。
2. 整理大纲。
3. 润色正文。
4. 生成搜索摘要。

搜索侧：

1. 理解搜索意图。
2. 扩展相关表达。
3. 对候选文章重排。
4. 生成推荐理由。

治理侧：

1. 查看 AI 配置状态。
2. 记录 AI 调用日志。
3. 后续可扩展采纳记录和问题反馈。

### 5.4 互动功能

互动功能保持轻量：

| 功能 | 产品含义 |
| --- | --- |
| 点赞 | 表示文章有帮助 |
| 收藏 | 表示以后还想看 |
| 评论 | 表示补充、提问或交流 |
| 评论审核 | 保证平台基础治理 |

当前不扩展关注、私信、粉丝体系，避免项目从知识写作与搜索平台膨胀为完整社区产品。

### 5.5 后台治理功能

后台治理功能包括：

1. 用户管理。
2. 文章管理。
3. 评论管理。
4. 分类管理。
5. 标签管理。
6. 知识合集管理。
7. AI 状态查看。

这些能力的价值在于保证系统可管理、可演示、可审查，而不是让普通读者通过后台结构理解内容。

## 6. 分类、标签、知识合集的重新定位

### 6.1 分类

分类不再是普通读者的主要入口。

它主要承担后台治理作用：

- 帮管理员管理内容方向。
- 帮课程演示说明数据结构。
- 保留传统内容组织能力。

前台可以保留分类页面，但不应该让分类成为首页核心。

### 6.2 标签

标签主要服务搜索辅助。

在传统博客中，标签常常需要作者手动精细维护；但在本项目中，读者主要通过自然语言搜索找内容。因此标签不应该成为作者的负担。

标签可以继续存在于数据库中，作为搜索召回和后台管理字段。未来可以由 AI 辅助维护，但不必把“标签推荐”作为写作页主功能强调。

### 6.3 知识合集

知识合集来自原“专栏”能力。

它不再是全站主要导航，而是作者组织个人知识体系的方式。

例如：

- Flask 项目实践。
- 数据库设计笔记。
- 软件工程课程材料。
- AI 协作开发记录。

读者主要通过搜索找到文章；如果认可作者，再进入作者主页查看其知识合集。

这种定位保留了原有专栏能力，也解决了“专栏和分类看起来越来越奇怪”的问题。

## 7. 数据与架构支撑

### 7.1 当前技术架构

项目继续使用 Flask + Jinja2 + SQLAlchemy + SQLite 的服务端渲染单体架构。

该架构适合当前课程项目，因为：

1. 启动简单。
2. 依赖较少。
3. 易于本地演示。
4. 代码结构清晰。
5. 便于展示从需求、设计、实现到测试的完整链路。

当前不引入前后端分离、微服务、任务队列或向量数据库。这不是技术能力不足，而是产品阶段和课程交付目标决定的取舍。

### 7.2 核心数据对象

当前核心数据对象包括：

| 对象 | 作用 |
| --- | --- |
| User | 用户、作者、管理员身份，以及 Markdown 知识主页 |
| Article | 文章内容、状态、摘要、AI 搜索摘要、阅读和互动计数 |
| BlogColumn | 知识合集，组织作者文章 |
| Category | 后台分类治理 |
| Tag | 搜索辅助标签 |
| Comment | 评论与审核 |
| Like | 点赞 |
| Favorite | 收藏 |
| AiLog | AI 调用记录 |

其中最能体现新产品基线的是：

- `User.profile_markdown`：支撑 Markdown 个性化知识主页。
- `Article.ai_search_summary`：支撑发布后搜索摘要。
- `Article.ai_search_generated_at`：记录搜索摘要生成时间。

### 7.3 搜索摘要为什么重要

如果只搜索标题和正文，系统会遇到两个问题：

1. 用户搜索表达和文章原文表达不一致。
2. 长正文中有很多噪声，搜索系统难以判断文章真正解决什么问题。

搜索摘要的作用是把文章转换成更适合搜索理解的“知识特征描述”。它不是给页面凑文案，而是系统理解文章的中间层。

因此，搜索摘要是本项目区别于普通博客的关键数据资产。

## 8. 项目边界

为了让项目保持清晰，本项目明确不做以下内容：

1. 付费、广告和商业化变现。
2. 私信、关注、粉丝体系。
3. 热榜和复杂推荐算法。
4. 问答社区。
5. 生产级高并发部署。
6. 微服务拆分。
7. 前后端完全分离。
8. 当前阶段引入向量数据库。
9. 多模型供应商复杂切换。
10. 流式 AI 输出。

这些能力并非没有价值，而是会把项目从“AI 知识写作与搜索平台”扩张成另一个更大的系统。当前阶段最重要的是让主闭环成立、可演示、可解释、可追溯。

## 9. 课程展示价值

本项目适合作为软件综合实践课程项目，是因为它同时具备产品完整性和工程可说明性。

### 9.1 产品完整性

它不是单页 Demo，而有完整用户链路：

1. 游客搜索。
2. 阅读文章。
3. 注册登录。
4. 写作发布。
5. AI 辅助。
6. 互动反馈。
7. 后台管理。

### 9.2 技术完整性

它包含 Web 系统常见模块：

- 路由。
- 模板。
- ORM。
- 用户登录。
- 权限控制。
- CSRF。

## 10. 当前成熟度判断

从产品闭环角度看，当前项目已经具备最小完整闭环：

| 闭环环节 | 当前状态 |
| --- | --- |
| Markdown 写作 | 已支持基础写作和渲染 |
| AI 辅助写作 | 接口存在，真实调用需配置验证 |
| 发布后搜索摘要 | 已支持，含本地降级 |
| 自然语言搜索 | 已支持 AI 搜索入口和传统降级 |
| 阅读互动 | 已支持点赞、收藏、评论 |
| 作者主页 | 已支持 Markdown 主页 |
| 后台治理 | 已支持基础治理 |

仍需后续验证或增强：

1. 真实 AI Key 下的摘要质量。
2. 真实网页资料搜索可用性。
3. AI 搜索重排效果。
4. 完整 E2E 测试。
5. 浏览器视觉验收。
6. AI 日志采纳闭环。

因此，当前项目可以表述为：

> 已经完成 AI 驱动知识写作与搜索平台的核心代码闭环；真实 AI 服务质量和完整验收证据仍需进一步测试确认。

## 11. 后续演进建议

后续不建议继续盲目加功能，而应围绕主闭环做增强。

优先级建议如下：

### P0：完成验收

1. 配置真实 AI Key，验证搜资料、润色、大纲、搜索摘要。
2. 验证自然语言搜索和 AI 重排。
3. 运行完整 E2E 测试。
4. 做主要页面视觉验收。

### P1：增强闭环质量

1. 完善 AI 日志采纳记录。
2. 增加搜索摘要重新生成入口。
3. 优化搜索结果解释。
4. 增加文章发布后的摘要预览。
5. 优化 Markdown 写作体验。

### P2：搜索能力升级

1. 评估轻量全文检索。
2. 评估向量检索。
3. 评估搜索排序中引入点赞、收藏、评论权重。

P2 能力只有在 P0 和 P1 完成后才值得考虑。否则项目会再次扩散，失去当前已经收束出来的清晰主线。

## 12. 总结

本项目最终应被理解为：

> 一个以自然语言搜索为入口、以 Markdown 写作为核心、以 AI 搜索摘要为连接层、以阅读互动为反馈机制的知识写作与搜索平台。

它的价值不在于复制传统博客平台，也不在于炫耀 AI 功能，而在于把 AI 放到知识流转的关键位置：

- 写作前，AI 帮作者搜资料和搭结构。
- 写作中，AI 帮作者润色表达。
- 发布时，AI 总结文章特征。
- 搜索时，AI 理解读者问题并匹配文章。
- 阅读后，用户互动反馈文章价值。

这条链路就是“稷下”的产品灵魂。

只要后续开发继续围绕这条链路推进，项目就会保持清晰、完整、可演示，也能在课程答辩中说明它不仅是一个能运行的 Web 系统，更是一个有明确产品逻辑和工程治理体系的 AI 知识平台。
