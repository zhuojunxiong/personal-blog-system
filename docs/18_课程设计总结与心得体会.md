## 一、前言

从零开始构建一个完整的 Web 应用系统，是我在大学生涯中最具挑战性也最有收获的一次实践。最初选择"博客系统"作为课程设计题目时，我担心过这个选题是否太平凡——毕竟博客系统几乎是每个 Web 开发学习者都会做的项目。但随着项目的推进，我在传统的博客基础上融入了 AI 写作辅助和智能搜索能力，最终交付了一个有产品辨识度的"AI 驱动知识写作与搜索平台"，389 个测试用例全部通过。

回想这几个月从需求分析、架构设计、编码调试、测试修复到文档交付的全过程，感触良多。以下是我在这段经历中的主要收获和思考。

## 二、技术层面的收获

### 2.1 从"能跑就行"到"工程化思维"的转变

在之前的课程作业中，我的代码风格基本是"功能实现即可"。变量命名随意、没有测试、异常处理缺失、配置硬编码——这些在本次课程设计中都成了实打实的教训。

**印象最深的一课**：系统最初上线时，每次重启 Flask 应用，所有用户都会被强制退出登录。原因是我把 `SECRET_KEY` 写成了每次启动随机生成。这个问题让我第一次真正理解了"配置管理"不是纸上谈兵——`instance/` 目录、环境变量、密钥持久化，这些概念从课本上的名词变成了实际踩过的坑。

**核心转变**：

| 之前的我 | 现在的我 |
|----------|---------|
| 代码能跑就行 | 考虑异常路径、边界条件、降级策略 |
| 手动测试几个页面 | 写 389 个自动化测试用例 |
| 配置写死在代码里 | 环境变量 + 文件持久化 + 测试配置覆盖 |
| 出错了不知所措 | 看日志、定位根因、写防御性代码 |
| 没有文档 | 17 份正式文档，形成可追溯链路 |

### 2.2 Flask 全栈开发的系统掌握

通过这个项目，我对 Flask 生态有了从"会用"到"理解"的跃升：

**应用工厂模式**：`create_app()` 不只是教材上的一页——我亲身体验了它如何让测试环境注入独立配置，如何避免循环导入。理解了"为什么"之后，才知道"怎么做"才是对的。

**Blueprint 模块化**：将系统拆分为 11 个 Blueprint（public、auth、user、article、category、tag、column、comment、admin、dashboard、ai），每个模块独立路由、独立 Service，相互之间通过明确的接口协作。这种组织方式让近万行代码的项目始终保持清晰的结构。

**Service 层的价值**：把业务逻辑从路由中抽离到 Service 层，一开始觉得多此一举。直到需要写测试时，才体会到 Service 层的可测试性——不需要模拟 HTTP 请求，直接调用函数、断言返回值，测试编写效率提升数倍。

**SQLAlchemy ORM 的深入理解**：
- 关系映射（一对多、多对多）的实际应用
- `onupdate` 在 Python 层触发而非数据库层的陷阱
- N+1 查询问题的发现和修复过程
- `flush()` vs `commit()` 的事务边界理解
- SQLite 的 `ALTER TABLE` 限制及其应对

### 2.3 AI 集成的实践经验

这是项目中最具特色也最富挑战的部分。将 AI 能力融入传统 Web 应用，我学到了：

**Prompt 工程不是简单的"问问题"**：为了获得稳定的 JSON 输出，需要明确指定格式、提供示例、设置合理的 temperature（审核用 0.1，润色用 0.7），还要处理模型输出的 markdown 代码块包装。`_parse_json_list()` 和 `_parse_json_dict()` 的容错逻辑就是反复调试后的产物。

**优雅降级比完美可用更重要**：AI 服务是外部依赖，不可控因素太多——API Key 未配置、网络超时、服务限流、返回格式异常。我的设计原则是"AI 增强而非必需"：每个 AI 调用都有独立的 try/except，失败时不影响核心业务流程。这个原则让我在开发调试阶段可以关闭 AI（`AI_ENABLED=0`）专注调试业务逻辑，而不被 AI 调用干扰。

**智能搜索的流水线设计**：将 AI 搜索拆分为"意图理解 → 关键词扩展 → SQL 召回 → AI 重排序"四个阶段，每个阶段独立降级。这个设计思路来自对搜索引擎架构的学习——即使 AI 全部不可用，传统 SQL ILIKE 搜索仍然可用。

### 2.4 测试工程的从零开始

在本次课程设计之前，我从未系统性地编写过测试。284 个 pytest 用例 + 84 个 E2E 用例，是我在测试领域从 0 到 1 的突破。

**学到的关键认知**：

- **函数级隔离是测试的基石**：每个测试使用独立的内存 SQLite —— `scope="function"` + `db.create_all()` / `db.drop_all()`，确保测试之间零干扰。没有这个基础，300 个测试不可能稳定通过。
- **Fixture 体系降低测试编写成本**：预定义了 `admin_user`、`normal_user`、`published_article` 等 fixture，写新测试时直接声明依赖即可，不用重复构造数据。
- **E2E 测试覆盖真实业务流程**：pytest 测试验证函数逻辑，E2E 测试验证完整链路（注册 → 登录 → 写文章 → 发布 → 评论 → 点赞 → 管理员审核）。两者互补，缺一不可。
- **测试是最好的文档**：新功能开发时，先写测试明确预期行为，再写代码满足测试。这种方式让代码意图非常清晰。

## 三、工程素养的提升

### 3.1 问题定位与调试能力

7 个已修复的缺陷，每一个都是一次完整的"发现问题 → 定位根因 → 设计方案 → 实现修复 → 验证效果"循环。

**调试方法的积累**：

- SQLite 空库崩溃 → 学会了检查数据库文件状态、理解 SQLite 自动创建文件的特性
- Session 全失效 → 学会了排查 SECRET_KEY 稳定性、理解 Flask Session 签名机制
- N+1 查询 → 学会了开启 SQL 日志、识别和优化冗余查询
- CSRF 400 错误 → 学会了理解错误处理器本身也会出错、CSRF 特殊处理方式

**最重要的体会**：Bug 不可怕，可怕的是不知道 Bug 从哪来。建立了"异常处理 → 日志记录 → 状态追踪"的调试链路后，大多数问题都能在几分钟内定位。

### 3.2 文档驱动的开发习惯

17 份文档的产出过程，让我完成了从"代码写完就完事"到"文档是交付物的一部分"的心态转变。

**文档写作的收获**：

- **需求规格说明书**：学会了用结构化的方式描述功能需求，区分"用户需要什么"和"怎么实现"
- **概要设计说明书**：学会了画架构图、描述模块职责、标注设计边界
- **ADR（架构决策记录）**：学会了记录技术选型的上下文、备选方案和决策理由——这对未来的自己和接手者都极为重要
- **测试报告**：学会用量化数据说话——"通过了"不如"284 个用例 74 秒执行完毕 0 失败"
- **调试分析文档**：学会将踩过的坑转化为可复用的经验，而不是"又浪费了半天"

### 3.3 时间管理与项目规划

课程设计的时间跨度长、任务种类多（需求、设计、编码、测试、文档、答辩准备），需要合理分配精力：

- **前期**（需求 + 设计）：投入 30% 时间，把方向定清楚，避免后期返工
- **中期**（编码 + 调试）：投入 40% 时间，这个阶段最密集也最容易出问题
- **后期**（测试 + 文档）：投入 30% 时间，测试发现的问题往往需要回头改代码

最深体会：**前期想清楚比后期改得快重要得多**。需求定偏了，代码写得再好也没用。

## 四、对 AI 辅助开发的理解

本次课程设计的一个特色环节是使用 AI Agent（architect、frontend、tester、reviewer、requirement）辅助开发过程。这让我对"AI 能做什么、不能做什么"有了切身体会。

### 4.1 AI 擅长的事

- **快速生成模板代码**：路由、模型、表单校验等模式化代码，AI 可以快速生成框架，人工只需调整业务细节
- **文档结构梳理**：AI 能帮助整理文档大纲、统一术语、检查前后矛盾，大幅降低文档写作的体力消耗
- **测试用例扩展**：给定核心用例后，AI 能快速生成边界条件、异常路径的补充用例
- **代码审查**：AI 能发现一些人工容易忽略的问题（如缺少 `is_active` 检查、N+1 查询）

### 4.2 AI 不擅长的事

- **理解业务上下文**：AI 不知道"这个功能对于课程项目来说是否过度设计"，需要人来判断优先级
- **架构决策**：AI 能列出选项，但无法权衡"课程交付时间"和"架构完美度"之间的取舍
- **验证代码是否真的能跑**：AI 生成的代码必须经过实际运行验证，不能盲目信任
- **理解"不做什么"**：AI 倾向于不断加功能，但好的产品往往在于知道什么不该做

### 4.3 人机协作的最佳实践

经过本次实践，我认为 AI 辅助开发的正确姿势是：

> **人定方向，AI 做执行；人做决策，AI 给建议；人验证结果，AI 辅助检查。**

把 AI 当作一个不知疲倦但缺乏判断力的初级工程师——它能帮你写很多代码，但每行都需要你理解和确认。

## 五、心态与感悟

### 5.1 从"赶作业"到"做产品"的心态转变

说实话，项目初期我的心态是"赶紧做完好交差"。但当我发现系统能稳定运行、AI 搜索真的能理解用户意图并返回相关文章时，心态不知不觉变成了"这个功能还能更好"。

当首次进入页（Landing Page）设计完成，AI 写作面板集成成功，389 个测试全部通过的那一刻——我第一次觉得这不是一份作业，而是一个我真正用心打造的、完整的产品。

### 5.2 面对困难的态度

项目过程中有太多次"卡住了"的时刻：

- 第一次看到 27 个 E2E 测试失败时的无力感
- `no such table` 崩溃时完全不知道从哪里开始排查
- SECRET_KEY 导致 Session 全失效，改了好几处代码才发现根因

现在回头看，**每个让你头疼的 Bug，修完之后都变成了你理解最深的那块知识**。这大概就是"踩坑"的意义。

### 5.3 对"软件工程"四个字的重新理解

以前总觉得"软件工程"就是写文档、画图、走流程，是拖慢开发速度的东西。做完这个项目后我完全改变了看法：

- **测试不是负担，是底气**：389 个测试全部通过后，我敢放心改代码，因为任何回归都能第一时间发现
- **文档不是多余，是传承**：等过几个月再回头看这个项目，文档能让我快速回忆当时的决策和设计
- **分层不是教条，是生存策略**：当项目大到一定程度，没有分层就会陷入"改一处崩一片"的困境
- **降级不是妥协，是成熟**：优雅降级意味着承认外部依赖不可靠，并为此做好了准备
