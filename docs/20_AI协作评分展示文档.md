### 1.1 发现并纠正 AI 输出错误（共计 10 处）

#### 错误 1：`admin_required` 装饰器缺少 `is_active` 检查（安全漏洞）

| 项目 | 内容 |
|------|------|
| **发现场景** | Reviewer Agent 代码审查 |
| **AI 原始输出** | 装饰器仅检查 `is_authenticated` 和 `is_admin` |
| **错误类型** | 逻辑漏洞 — 安全缺陷，严重程度 🟠 高 |
| **人发现过程** | 审查 [app/admin/decorators.py](app/admin/decorators.py) 时，对照 `User` 模型发现 `is_active` 属性（依赖 `status == "active"`）在装饰器中未被调用，被禁用的管理员仍能访问后台 |
| **人纠正** | 新增第三层检查：`if not current_user.is_active: flash("您的账号已被禁用")` |
| **修复结果** | 禁用管理员无法再访问后台 |
| **对应 BUG** | BUG-004，记录于 [tests/测试记录.md](tests/测试记录.md) 行 224 |

#### 错误 2：`approved_comment_count` N+1 查询（性能缺陷）

| 项目 | 内容 |
|------|------|
| **发现场景** | Reviewer Agent 代码审查 |
| **AI 原始输出** | `Comment.query.filter_by(...).count()` 作为 `@property`，模板每渲染一篇文章触发一次独立 SQL |
| **错误类型** | 性能问题 — N+1 查询，20 篇文章 = 21 次 SQL |
| **人发现过程** | 审查模板渲染逻辑，意识到 Jinja2 模板中 `{{ article.approved_comment_count }}` 每次调用触发 `SELECT COUNT(*)` |
| **人纠正** | 改用 `db.session.query(db.func.count(Comment.id)).filter(...).scalar()`，标注需配合 `joinedload` 优化 |
| **对应 BUG** | BUG-005，记录于 [tests/测试记录.md](tests/测试记录.md) 行 225 |

#### 错误 3：`ensure_sqlite_schema()` 无法处理完全空库（边界遗漏）

| 项目 | 内容 |
|------|------|
| **发现场景** | T002 启动验证，浏览器报 `no such table: articles` |
| **AI 原始输出** | 只处理"表已存在但缺少列"的 ALTER TABLE 场景，不处理"完全空库"的初始建表 |
| **错误类型** | 逻辑漏洞 — 边界条件未覆盖，严重程度 🔴 致命 |
| **人发现过程** | `git restore` 后数据库虽存在但所有表丢失，`sqlite_master` 返回空 |
| **人纠正** | 要求 AI 增加步骤：先检查核心表是否存在 → 不存在则 `db.create_all()`；同时在 `user_loader` 增加防御性重试 |
| **对应 BUG** | BUG-001，记录于 [docs/11_AI协作记录.md](docs/11_AI协作记录.md) 行 207-217 |

#### 错误 4：AI 建议搜索页双轨并行（产品设计冗余）

| 项目 | 内容 |
|------|------|
| **发现场景** | CR-013 AI 搜索局部前后端分离 |
| **AI 原始输出** | 在搜索页同时保留传统 `<form>` 和 AI 异步搜索，双轨并行 |
| **错误类型** | 产品设计冗余 — 用户体验不一致 |
| **人发现过程** | 判断双轨搜索会使用户困惑：同一页面两套搜索逻辑，输入框行为和结果展示不同 |
| **人纠正** | 要求改为纯异步 AI 搜索，传统搜索降级在 JS 层自动处理，不暴露双输入框 |
| **修复结果** | [app/templates/v041/search_results.html](app/templates/v041/search_results.html) + JS 统一搜索入口 |

#### 错误 5：写作页分类解析的类型不匹配

#### 错误 6：SECRET_KEY 每次重启重新生成（配置缺陷）

| 项目 | 内容 |
|------|------|
| **发现场景** | 开发过程中频繁重启导致 Session 全失效 |
| **AI 原始输出** | `Config.SECRET_KEY = os.getenv("SECRET_KEY") or secrets.token_hex(32)` — 每次进程启动生成新 key |
| **错误类型** | 配置缺陷 — 影响所有已登录用户 |
| **人发现过程** | 每次重启 Flask 后需要重新登录，追踪到 Flask Session cookie 签名验证失败 |
| **人纠正** | 实现三层优先级：环境变量 > `instance/.secret_key` 文件 > 自动生成并持久化到文件 |
| **对应 BUG** | BUG-003，记录于 [tests/测试记录.md](tests/测试记录.md) 行 223 |

### 1.3 AI 能力边界分析（共计 5 次）

#### 边界分析 1：AI 不能替代人工做产品判断

| 项目 | 内容 |
|------|------|
| **分析场景** | v0.5.1 → v1.0 产品基线化 |
| **分析结论** | AI 能读取代码、整理功能清单、列出候选需求，但**不能判断**"课程交付应该包含哪些功能"——这需要理解评分标准、时间预算、答辩策略，只有人能做 |
| **人工决策** | 人确认 v1.0 范围为 F001-F050，N001-N012 分流到 v1.1/v2.0 |
| **记录位置** | [docs/11_AI协作记录.md](docs/11_AI协作记录.md) 第 10.3 节：明确"项目负责人负责阅读 7 份系统理解文档，完成人工确认和后续决策" |

#### 边界分析 2：AI 不能替代实际运行验证

| 项目 | 内容 |
|------|------|
| **分析场景** | AI 功能测试与验收 |
| **分析结论** | AI 能生成测试代码、分析代码逻辑、推断预期行为，但**不能替代**实际运行——AI 不知道真实 API Key 是否有效、不知道网络是否可达、不知道浏览器渲染效果 |
| **人工决策** | 所有测试必须实际执行并记录结果。AI 协作记录中明确标注"未执行"vs"已通过"，测试报告明确标注"浏览器截图验收：待执行" |
| **记录位置** | [docs/11_AI协作记录.md](docs/11_AI协作记录.md) 第 10.4 节（7 项未做的事情）+ [docs/09_测试报告.md](docs/09_测试报告.md) 多处标注 |

| **人工决策** | 人先明确需求范围为"优化公开作者主页 `/users/<id>`"，AI 再进入执行 |
| **记录位置** | [docs/11_AI协作记录.md](docs/11_AI协作记录.md) 第 13.1 节 |

| 项目 | 内容 |

**协作节奏**：整个过程人的主导和AI的执行是交替进行的——人在关键节点做决策、定方向、验证结果，AI在决策之间的执行阶段做大量机械性工作。

**具体流程说明**：

#### 第 1 轮（👤 人主导）— 定方向、建体系

人在这一轮独立做全部关键决策：选定主仓库策略（ADR-001）、从 5 个技术方案中选定保留 Flask（ADR-002）、建立半自动工程化开发体系（ADR-003）、制定产品基线化策略（ADR-004）。AI 的辅助仅限于整理需求现状和生成框架文档——因为人对系统还不够了解，需要 AI 帮忙梳理。

这轮没有让 AI 写代码，只让 AI 做"阅读理解+整理"的工作。

#### 第 2 轮（🤖 AI 主导）— AI 反向阅读系统

人发现自己对现有代码的理解不够深入，于是让 AI 用 5 个 Agent 反向阅读整个代码库，生成 7 份系统理解文档。AI 做的事情人做不了——一次性通读 91 个文件、梳理 50 个功能需求、建立路由-页面-数据模型的映射关系。

AI 生成完毕后，人**阅读全部 7 份文档**，然后独立确认：v1.0 做哪些、不做哪些、哪些放 v1.1、哪些放 v2.0。12 项明确排除。

这轮 AI 的产出量最大，但最终决策权在人。

#### 第 3 轮（👤 人主导）— 启动验证、手动检查

人操作启动项目、配置 API Key、浏览器逐页验收。人通过手动检查发现了 9 个视觉问题（AI 之前没有发现）。AI 在这轮的职责是诊断问题根因（如数据库空库的原因）和整理变更记录。

这轮是典型的"人验证 AI 之前的代码产物"——AI 写代码、人找问题。

#### 第 4 轮（👤 人决策）— 产品主线收束

人独立决策：将项目从"多用户博客"收束为"AI 驱动知识写作与搜索平台"。人决定：8 种 AI 能力只保留 4 项核心、分类标签专栏前台弱化、专栏改为知识合集。AI 的职责是**同步执行**——人决定方向，AI 同步修改代码和 17 份文档。

#### 第 5 轮（👤 人主导）— 教师材料处理

人决定不照搬全部教师材料，而是定 6 条原则做项目化吸收。AI 按照这些原则，将教师材料转化为 5 个 Agent prompt + 5 个 Skill 规程 + 使用记录 + 交付检查清单。人审核定稿，尤其强调区分"已建立入口"和"未实际运行"的口径。

#### 第 6 轮（🤖 AI 主导执行）— 代码密集实现

AI 按照已经确认的 CR-010~013 需求，执行代码实现。这一轮的 AI 工作量最大：重写模板、实现 AI 审核和质量诊断、做搜索页局部 API 化改造、生成测试用例。

人在这轮的职责是**验证**：用真实 DeepSeek 测试 AI 审核（正常文章→passed，赌博广告→suspected）、验证 AI 质量诊断（72/100 评分）、重写过时的 E2E 测试、执行全部 389 个测试。

#### 第 7 轮（👤 人主导）— 最终文档定稿

人口述调试经验、系统评价、心得体会。AI 整理成正式文档并润色表达。人逐篇审核文档口径，确保"不夸大 AI 作用、不伪造测试结果、不把计划写成已完成"。

---

**整个过程的协作本质**：

```text
人决策 → AI执行 → 人验证 → 人再决策 → AI再执行 → 人再验证 → …循环
```

- 人对系统不了解时 → 让 AI 反向阅读、生成理解文档（第 2 轮）
- AI 代码有缺陷时 → 人手动验收、发现 9 个视觉问题（第 3 轮）
- 产品方向需要收束时 → 人独立决策，AI 同步执行（第 4 轮）
- 对外部材料需要处理后 → 人定原则，AI 按原则转化（第 5 轮）
- 代码需要密集实现时 → AI 批量生成，人逐个验证（第 6 轮）
- 文档需要出最终版时 → 人口述经验，AI 整理成文（第 7 轮）

**7 轮中没有一轮是"AI 做完直接交付"，每一轮都是人验收后才进入下一轮。**

## 四、核心论证

本项目的 AI 协作模式可以概括为一句话：

> **"人是架构师和决策者，AI 是高效的工具和助手"**

具体体现为五个层次：

**第一层：人始终保持对关键决策的控制权。** 技术栈选择（ADR-002）、产品定位（CR-009）、功能范围（CR-003）、安全策略（BUG-004）、教师资料纳入方式（CR-002）——全部由人独立决策。AI 只提供信息、方案对比和影响评估，供人选择。

**第二层：人始终保持对 AI 输出的批判态度。** 10 处发现并纠正 AI 错误，覆盖安全漏洞（`admin_required` 缺 `is_active`）、性能问题（N+1 查询）、边界遗漏（空库崩溃）、产品设计（双轨搜索）、类型安全（字符串 ID）、配置缺陷（SECRET_KEY）、测试失效（E2E 未适配）、UI 缺陷（4 类视觉问题）。

**第三层：人明确了解 AI 的能力边界。** 5 次正式的能力边界分析，明确 AI 不能做产品判断、不能替代运行验证、不能理解模糊需求、不能自动完成项目、不能判断外部资料可信度。这些边界被写入 AGENTS.md、每份 CR 文档，以及 AI 协作记录的"明确没有做的事情"清单。

**第四层：人建立了系统的协作流程。** 7 轮迭代，每轮遵循"需求→设计→实现→审查→文档"的完整循环。每轮开始前明确输入范围、禁止事项和验收标准；每轮结束后记录"已执行"与"未执行"、"人完成"与"AI 辅助"。

**第五层：人通过约束和禁止事项管理 AI。** AGENTS.md 第 7 节禁止事项、每份 CR 的"不纳入范围"、每轮 AI 协作记录的"明确没有做的事情"——形成了对 AI 行为的系统性约束，确保 AI 在可控范围内工作。

**本项目不是"AI 自动完成了项目"，而是"人在 AI 的高效辅助下，以更高的质量和更完整的工程链路完成了项目"**——这正是 AI 协作课程希望培养的核心能力。
