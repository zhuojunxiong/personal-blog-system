# CR-003 当前系统理解补课、需求澄清与新增功能评估

## 0. 使用说明

本文用于记录 `work/v1.0-course-delivery` 分支下进入 v1.0 课程交付完整版前的当前系统理解补课、需求澄清与新增功能评估。

本文只创建变更请求，不修改业务代码，不代表候选需求已经实现，也不代表允许直接进入代码实现。候选需求如需进入实现，必须另行创建后续独立 CR，并完成需求、设计、数据库、测试、文档和 ADR 判断。

本文不重写 `docs/product-rebaseline` 全套文档，只评估是否需要在既有产品重新基线化结论上做局部说明补充。本文不读取或修改 `software-practice-records`。本文继续遵守 ADR-002 方案 B：保留 Flask + Jinja2 + SQLAlchemy + SQLite，在测试保护、需求确认和 ADR 约束下做受控局部修改。

## 3. 变更背景

- 背景说明：当前进入 v1.0 课程交付完整版前，需要确认现有需求是否足够清晰，是否存在必须补充的新功能。当前项目负责人对原版本的技术架构、系统架构、需求、软件设计、模块划分和代码实现理解不足；此前开发更多依赖 AI 生成前端、需求和 AI 功能描述。因此，在判断是否新增需求和功能前，必须先反向理解当前系统，补齐对已有代码、页面、模块、数据和需求追溯关系的认知。v1.0 的目标是可运行、可演示、可测试、可答辩、可追溯的课程交付收束，不是无边界新增功能、重写系统或更换技术路线。
- 触发来源：
  - `AGENTS.md` 对需求先行、CR、ADR、测试保护、人工确认和禁止事项的约束。
  - `docs/change-requests/CR-001-下一版本启动与范围确认.md` 对 v1.0 课程交付完整版范围的确认。
  - `docs/功能展示清单.md` 对当前功能展示状态、需验证项和暂不纳入项的整理。
  - `docs/07_需求规格说明书.md` 对 F001-F050 和 N001-N012 的正式需求口径。
  - `docs/product-rebaseline/04_功能清单与取舍矩阵.md` 对保留、完善、推迟和暂不纳入功能的取舍判断。
  - `docs/product-rebaseline/10_下一版本范围建议.md` 对 v0.6 稳定演进、v0.7 产品重构和 v1.0 课程交付版本的范围建议。
- 当前问题或机会：
  - 项目负责人需要先掌握当前系统事实，避免在不理解现有架构、模块和代码边界的情况下继续追加功能。
  - 部分已实现需求仍存在规则、展示口径或测试证据不清楚的问题。
  - 部分 AI、个人中心、日志、启动、测试、视觉和文档链路能力存在候选价值，但不能被写成已经实现。
  - v1.0 只应纳入课程交付必要的系统理解补课、需求澄清、验收标准和文档补充；涉及代码实现的新增能力应进入后续独立 CR。

## 4. 阶段 A：当前系统理解补课

进入需求澄清和新增功能评估前，必须先完成当前系统理解补课。该阶段目标是用项目负责人能理解的方式，把当前系统“是什么、怎么分层、页面怎么进、数据怎么连、需求落在哪里、风险在哪里”讲清楚。

| 输出项 | 说明 | 状态要求 |
| --- | --- | --- |
| 当前系统总览 | 说明系统定位、用户角色、主业务闭环、当前版本边界和课程交付目标。 | 只能基于当前仓库代码和正式文档，不补写幻想功能。 |
| 目录结构与模块说明 | 说明 `app/`、配置、脚本、模板、静态资源、测试和文档目录的作用。 | 用通俗语言解释模块职责和边界。 |
| 技术架构通俗解释 | 解释 Flask、Jinja2、SQLAlchemy、SQLite、Blueprint、Service、模板渲染、环境变量等如何协作。 | 继续遵守 ADR-002 方案 B，不引入换栈结论。 |
| 路由-页面-模板映射 | 追踪主要 URL、路由函数、页面模板、用户角色和对应功能编号。 | 不要求覆盖每个内部细节，但要覆盖课程演示主路径。 |
| 数据模型与数据库关系 | 说明用户、文章、专栏、分类、标签、评论、点赞、收藏、AI 日志等模型关系。 | 不新增模型；ReadingHistory 只能标注为候选。 |
| 需求-模块-代码追踪表 | 把 F001-F050、N001-N012 与主要模块、路由、模板或脚本建立追踪关系。 | 不把候选需求写成已实现。 |
| 当前系统风险与不确定项 | 汇总 AI 调用、初始化、测试、视觉、权限、数据语义和文档口径风险。 | 用于后续需求澄清和测试保护。 |

阶段 A 的结论不是新增功能授权。若系统理解过程中发现疑似缺陷、缺口或新增需求，只能记录为风险、不确定项或候选需求，不能直接修改业务代码。

## 5. 阶段 B：需求澄清

只有完成阶段 A 的当前系统理解补课后，才允许手动补充用户原始需求想法，并将这些想法整理为可澄清、可评估、可验收的需求条目。

阶段 B 的处理原则：

| 原始想法类型 | 处理方式 | 是否允许直接实现 |
| --- | --- | --- |
| 对已有功能规则不清楚 | 标注为“需求澄清”，补充业务规则、验收标准和测试点。 | 不允许。 |
| 对页面或交互体验不满意 | 先记录问题、页面、影响范围和截图需求。 | 不允许；进入代码需后续独立 CR。 |
| 对 AI、搜索、日志或个人中心有新想法 | 先判断是 v1.0 必做、v1.0 可选还是未来版本候选。 | 不允许；涉及实现需后续独立 CR。 |
| 对数据库或模型语义有调整想法 | 先记录数据影响、迁移风险和 ADR 触发条件。 | 不允许；必须后续独立 CR 和 ADR 判断。 |
| 对课程交付材料有补充要求 | 可纳入 v1.0 文档、测试、Review 或 AI 协作记录范围。 | 仅限文档或验收记录，不修改业务代码。 |

阶段 B 必须继续区分“已实现”“需验证”“需求澄清”“候选需求”“未来版本”和“暂不纳入”。不得把用户原始想法直接写成当前系统已经具备的能力。

## 6. 阶段 C：新增功能评估

新增功能必须在阶段 A 和阶段 B 之后再评估，并按版本归类。归类结果只用于范围判断，不代表已经实现。

| 分类 | 含义 | 示例方向 | 处理原则 |
| --- | --- | --- | --- |
| v1.0 必做 | 直接影响课程交付可复现、可测试、可答辩、可追溯的事项。 | 系统理解文档、启动验收、测试记录、错误路径、README 校准、文档链路。 | 可进入 v1.0 文档或验收范围；涉及代码仍需独立 CR。 |
| v1.0 可选 | 对答辩展示有帮助，但不是最低交付前置。 | AI 真实调用演示、视觉样本验收、后台治理说明增强。 | 有时间和证据再做；不得影响主链路稳定。 |
| v1.1 候选 | 适合在 v1.0 稳定后小步增强的功能。 | 真实最近阅读、AI 日志采纳闭环、搜索体验增强、小范围 UI 优化。 | v1.0 不默认实现；后续独立 CR。 |
| v2.0 / 架构探索候选 | 可能改变架构、数据、部署或交互形态的探索。 | 多 Provider、流式输出、向量检索、移动端 API、任务队列。 | 未来版本评估，通常需要 ADR。 |
| 暂不纳入 | 与当前课程交付和博客主链路关系弱，或范围明显过大。 | 付费、广告、会员、私信、关注、热榜、问答社区、复杂推荐。 | 不进入当前 v1.0，也不写进已实现范围。 |

| project-requirements skill | 辅助从现有代码和文档反向理解需求、接口和流程。 | 不能替代当前仓库事实源。 |

## 9. 当前需求不清楚的类型

| 类型 | 说明 | 处理原则 |
| --- | --- | --- |
| 需求澄清 | 已有功能或候选功能的规则、边界、验收标准不够清楚。 | 可纳入 v1.0 文档澄清，不默认改代码。 |
| 证据缺口 | 功能接口或脚本存在，但启动、测试、AI 调用、视觉或截图证据不足。 | 可纳入 v1.0 验收和记录范围，结果必须真实。 |
| 文档口径冲突 | README、需求、展示清单或历史文档对同一能力表述不一致。 | 可纳入 v1.0 文档校准，不能伪造完成状态。 |
| 数据语义不清 | 收藏、最近阅读、AI 日志采纳等数据含义不够明确。 | 先需求澄清；若新增模型或字段，必须后续独立 CR 和 ADR 判断。 |
| 权限与可见性规则不清 | 禁用用户、禁用专栏、评论审核、删除分类/标签等前台表现不明确。 | v1.0 可补规则说明和测试用例；代码修改需后续独立 CR。 |
| AI 边界不清 | AI 接口、真实调用、失败降级、采纳结果和日志闭环边界不清。 | v1.0 只确认验收口径和降级说明；扩展 AI 架构进入未来版本。 |
| 未来功能误入当前版本 | AI 阅读助手、关注私信、热榜、复杂推荐、付费等容易扩大范围。 | 明确不进入当前 v1.0，保留为未来版本候选。 |
