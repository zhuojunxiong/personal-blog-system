# 需求变更记录

## 1. 文档状态

本文档用于 `v0.5.1-governance` 阶段记录产品重新基线化后发现的候选需求变更，承接功能取舍矩阵中的 CR、ADR 和测试保护建议。

依据范围：

1. `AGENTS.md`
2. `docs/product-rebaseline/04_功能清单与取舍矩阵.md`
3. `docs/product-rebaseline/06_课程验收目标映射.md`
4. `docs/change-requests/CR_TEMPLATE.md`

约束说明：

1. 本文只记录候选变更，不代表变更已经获批。
2. 本文不生成具体代码实现任务，不修改业务代码。
3. 本文不把未验证、部分实现或后续计划写成已完成。
4. 候选变更只有经过人工确认，并按需同步到正式需求、设计、CR 或 ADR 后，才能作为后续实现依据。
5. 本文不读取、不引用、不同步 `software-practice-records`。

## 2. 变更管理分类

| 分类 | 含义 | 处理原则 |
| --- | --- | --- |
| 只需文档修正 | 当前能力已存在或边界已明确，主要问题是 README、正式需求、启动指南、测试报告或交付说明口径不一致。 | 优先修正文档和追溯关系，不默认进入代码实现。 |
| 需要产品确认 | 涉及业务规则、角色边界、验收范围或是否纳入下一版本，需要人工先做产品判断。 | 确认前不得写入已批准需求，不得扩大实现范围。 |
| 需要设计调整 | 涉及页面流程、状态流转、数据语义、异常降级或跨模块协作，需要先补设计说明。 | 设计确认后再判断是否需要代码实现。 |
| 需要代码实现 | 当前只是部分实现、接口存在或后续计划，若决定纳入基线，才可能需要代码变更。 | 必须先有确认后的 CR、设计和测试计划；本文不拆实现任务。 |
| 需要 ADR | 涉及新增模型、字段语义、数据库变化、AI 搜索策略、AI 日志闭环或治理流程重大变化。 | 先写 ADR，再决定是否进入实现。 |
| 需要测试保护 | 若变更进入文档、设计或代码阶段，需要补自动化测试、手工验收、截图或演示证据。 | 不把历史通过或未运行测试写成当前通过。 |

## 6. 正式 CR 转化规则

1. `CR-CAND-*` 只是临时候选编号，不等同正式 CR 编号。
2. 候选变更进入正式流程前，应按 `docs/change-requests/CR_TEMPLATE.md` 补充完整字段。
3. 正式 CR 至少应说明变更背景、涉及需求编号、涉及页面或模块、产品影响、设计影响、数据库影响、测试影响、文档影响、是否需要 ADR、是否允许进入实现和人工确认结论。
4. 涉及模型、字段、数据库、AI 搜索策略、AI 日志闭环或治理流程重大变化时，应先写 ADR。
5. 未经人工确认的候选变更不得写入“已批准”“已实现”或“当前基线已包含”。
6. 如果候选变更最终被拒绝或暂缓，应保留原因，避免后续重复扩大范围。
