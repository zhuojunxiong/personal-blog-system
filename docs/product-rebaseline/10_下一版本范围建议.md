# 下一版本范围建议

## 1. 文档状态

本文档用于 `v0.5.1-governance` 阶段产品重新基线化完成后，形成下一实现版本的范围建议。

依据范围：

1. `AGENTS.md`
2. `docs/product-rebaseline/01_项目定位再分析.md` 到 `docs/product-rebaseline/09_软件设计影响分析.md`
3. `docs/04_未来需求与产品方向.md`
4. `docs/05_技术路线决策报告.md`
5. `docs/06_ADR/ADR-002-v0.6技术路线选择.md`

约束说明：

1. 本文只做下一版本范围建议，不代表已经开始实现。
2. 本文不修改业务代码，不提出当前立即编码结论。
3. 本文不读取、不引用、不同步 `software-practice-records`。
4. 下一实现版本仍需人工确认后，才能进入正式 CR、设计、测试和实现流程。
5. 若后续范围涉及模型、数据库、AI 搜索策略、AI 日志闭环或架构边界变化，应先补 ADR。
6. 若后续范围进入实现，应先明确测试保护和验收路径，不得把未运行测试写成当前通过。

## 4. 路线分析

### 4.1 v0.6 稳定演进

v0.6 稳定演进的核心目标是：在不破坏 v0.5.1 已有主业务闭环的前提下，把当前最影响课程验收的验证、文档、测试、AI 和演示证据补齐。

适合前提：

1. 人工确认下一阶段仍以课程实践交付和稳定演示为主。
2. 人工确认不在下一阶段更换技术栈、不前后端分离、不重写 v1.0。
3. 当前主业务闭环继续保留，重点处理 F036-F050 和 N001-N012。
4. AI 写作和 AI 搜索只作为验证或可选亮点，不作为创作和搜索主链路前置条件。

风险：

1. 若把 v0.6 写成已经开始实现，会与当前治理分支口径冲突。
2. 若同时纳入 ReadingHistory、AI 日志闭环、AI 搜索增强和 UI 大改，范围会膨胀。
3. 若未先执行测试和启动验证，后续小修也可能破坏已有演示链路。
4. 若 AI 真实调用依赖外部服务，现场演示仍需准备无 Key、失败和降级口径。

对课程验收的价值：

1. 补齐老师复现项目所需的启动、初始化、默认账号和演示数据说明。
2. 补齐测试报告、失败项、视觉验收和截图证据。
3. 统一版本口径，降低答辩时文档冲突风险。
4. 通过 AI 真实调用验收或降级说明，把 AI 从“不确定亮点”变成“可解释能力”。

对代码的影响：

1. 默认不改业务代码。
2. 若启动、测试或视觉验收发现缺陷，可通过正式 CR 做小范围修正。
3. 若采纳真实 ReadingHistory、AI 日志闭环或 AI 搜索策略调整，可能涉及模型、路由、Service、模板和测试，应先补 ADR 或设计说明。
4. 不引入新技术栈，不做大规模模板重写或数据库切换。

### 4.2 v0.7 产品重构

v0.7 产品重构的核心目标是：在稳定证据已经建立之后，对产品结构、页面体验和部分服务边界进行更系统的整理。

适合前提：

1. v0.6 范围中的启动、初始化、测试、文档和视觉验收已经形成当前证据。
2. 个人中心、真实阅读记录、收藏语义、AI 日志闭环、AI 搜索入口和后台治理规则已经人工确认。
3. 已有足够测试保护覆盖公开浏览、账号、创作、互动、后台、权限、安全和 AI 降级。
4. 已明确哪些重构是产品体验需要，哪些只是技术整理，避免无关重构。

风险：

1. 个人中心、AI、搜索、后台和 CSS/JS 如果同时重构，影响面较大。
2. 新增 `ReadingHistory` 或 AI 日志字段可能引入数据库变更和迁移问题。
3. 页面重构容易影响答辩截图、演示路径和已有测试。
4. 若缺少 ADR 和回滚方案，产品重构会偏离 ADR-002 的受控局部重构原则。

对课程验收的价值：

1. 可体现产品设计和软件设计迭代能力。
2. 可改善个人空间、搜索体验、后台治理说明和 AI 使用闭环。
3. 若时间充足，可提升系统完成度和答辩观感。
4. 但它不是最低课程通过的前置条件，不能替代启动、测试和正式文档证据。

对代码的影响：

1. 中到高，可能涉及 `user`、`public.search()`、`AIService`、`AiLog`、后台路由、模板和静态资源。
2. 若新增模型或字段，需先补 ADR、迁移或初始化策略、测试计划和回滚说明。
3. 不应改变当前 Flask + Jinja2 + SQLAlchemy + SQLite 技术路线。
4. 不应升级为前后端分离、微服务或重新开发。

### 4.3 v1.0 课程交付版本

v1.0 课程交付版本的核心目标是：把已经稳定的功能、测试、Review、AI 协作记录和项目总结打包成课程最终交付闭环。

适合前提：

1. 课程答辩或最终提交时间已经接近。
2. F001-F025 和 F038-F047 主链路保持稳定，至少有当前测试或手工验收记录。
3. F036-F050 的文档、测试、Review、AI 协作记录和总结已经明确最低交付范围。
4. AI 写作、AI 搜索和 AI 日志要么已有验证证据，要么清楚标注为可选亮点或未完成风险。

风险：

1. 若跳过 v0.6 稳定证据直接命名 v1.0，可能把未验证能力包装成最终完成。
2. 若在 v1.0 阶段继续引入新功能，会影响最终交付稳定性。
3. 若测试报告、Review 记录和 AI 协作记录仍为空，会削弱课程验收价值。
4. 若未明确未纳入范围，答辩中容易被追问 AI 阅读助手、商业化或复杂社区能力。

对课程验收的价值：

1. 最高。v1.0 直接面向课程交付、答辩和最终材料归档。
2. 可集中展示需求分析、概要设计、实现、测试、Review、AI 协作和总结闭环。
3. 可把产品边界、技术路线和暂缓范围讲清楚，体现范围控制能力。
4. 适合在功能稳定后作为交付版本，而不是作为重写版本。

对代码的影响：

1. 默认低到中，以缺陷修正、演示稳定和文档同步为主。
2. 不建议在 v1.0 阶段进行大范围产品重构或技术重构。
3. 若最终验收发现阻塞缺陷，应通过 CR 修复并补测试记录。
4. 不应把 v1.0 理解为重新开发、换栈或生产级平台化。

## 5. 推荐下一实现版本

推荐下一实现版本为：

```text
v0.6 稳定演进
```

推荐理由：

1. v0.6 最符合当前产品重新基线化结论：先稳定现有主链路，再补证据和小步演进。
2. v0.6 与 ADR-002 一致：保留当前技术栈，在测试保护、需求确认和 ADR 约束下做受控局部重构。
3. v0.6 能优先解决课程验收最紧迫的问题：启动、初始化、测试、视觉验收、README、正式文档链路和 AI 真实调用验证。
4. v0.6 不要求重写系统，不要求更换技术栈，不要求把 AI 搜索或 AI 写作变成稳定主链路。
5. v0.6 可以为后续 v0.7 产品重构和 v1.0 课程交付版本提供更可靠的证据基础。

推荐口径：

1. 本文只是推荐 v0.6 作为下一实现版本，不表示 v0.6 已经开始实现。
2. 进入 v0.6 前仍需人工确认范围、版本号、分支策略、CR、ADR 和测试计划。
3. 若课程答辩时间已经非常接近，人工可选择将 v0.6 稳定演进范围压缩后直接服务 v1.0 课程交付，但不建议跳过启动和测试证据。

## 7. 不纳入 v0.6 范围

以下内容不建议纳入推荐版本范围：

| 不纳入范围 | 原因 | 后续触发条件 |
| --- | --- | --- |
| 重新开发 v1.0 | 风险高，会破坏已形成主链路和追溯关系。 | 仅在现有系统无法支撑课程目标且有新 ADR 时评估。 |
| 更换 Flask、Jinja2、SQLAlchemy 或 SQLite | 当前问题主要是验证、文档和小范围规则，不是技术栈无法支撑。 | 出现移动端 API、生产部署、数据规模或课程明确要求时再 ADR。 |
| 前后端分离、微服务、任务队列 | 会显著扩大范围，不符合当前稳定演进目标。 | 未来有明确多客户端、异步任务或高并发需求时再评估。 |
| AI 阅读助手 F035 | 当前只是后续提示，未形成真实闭环。 | 人工确认进入远期版本，并补需求、设计、测试和必要 ADR。 |
| 多 Provider、流式输出、向量检索 | AI 基础调用和日志闭环尚未验收，不应提前扩大架构。 | F026-F034 验证稳定后再评估。 |
| 付费、广告、会员、收益分成 | 与当前课程验收和博客主链路无直接关系。 | 产品定位明确商业化后重新立项。 |
| 关注、私信、热榜、复杂推荐、问答社区 | 会把系统扩展为大型社区，超出当前基线。 | 人工确认系统方向从博客扩展为社区后再 CR/ADR。 |
| 大范围 UI 重做 | v0.6 重点是视觉验收和小修，不是重新设计整套页面。 | v0.6 验收后进入 v0.7 产品重构时评估。 |
| 默认实现 ReadingHistory | 当前只建议确认个人中心和收藏语义。 | 人工确认 N007，并补 CR、设计、ADR 判断和测试计划。 |
| 默认实现 AI 日志后台治理闭环 | v0.6 可先补需求和设计，不默认改模型或后台。 | 人工确认采纳、问题标记、后台查看和统计后再实现。 |

## 11. 阶段性结论

下一阶段最稳妥的建议是选择 `v0.6 稳定演进`，但该选择仍需人工确认后才能进入实现。

v0.6 不应被理解为已经开始开发，也不应被理解为重写、换栈或前后端分离。它更适合作为当前产品重新基线化之后的低风险实现版本：保留已有主业务闭环，优先补启动、初始化、测试、AI 验证、视觉验收、README 和正式文档链路，并在必要时通过 CR、ADR 和测试保护做受控小范围修正。

v0.7 更适合在 v0.6 证据稳定后进行产品重构；v1.0 更适合作为课程最终交付版本，而不是重新开发版本。
