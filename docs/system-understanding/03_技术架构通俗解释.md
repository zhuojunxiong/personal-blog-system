# 技术架构通俗解释

生成日期：2026-07-02

本文解释当前 Flask + Jinja2 + SQLAlchemy + SQLite 服务端渲染单体应用如何协作。本文只解释当前架构，不提出换栈，不修改业务代码，继续遵守 ADR-002 方案 B。

## 1. 当前架构像什么

可以把当前系统想成一家小型内容平台办公室：

| 技术对象 | 像什么 | 在系统里做什么 |
| --- | --- | --- |
| Flask | 总服务台 | 接收浏览器请求，决定交给哪个模块处理。 |
| Blueprint | 分部门窗口 | 把公开页、登录、用户、后台、AI 等 URL 分门别类。 |
| routes.py | 接待员 | 接请求、读参数、判断权限、调用服务、返回页面或 JSON。 |
| Service | 业务办事员 | 负责查询、校验、创建、更新、删除、AI 调用等复用逻辑。 |
| SQLAlchemy Model | 数据表说明书 | 用 Python 类描述用户、文章、评论等表和关系。 |
| SQLite | 文件柜 | 把数据保存在本地 `instance/personal_blog.sqlite` 文件中。 |
| Jinja2 Template | 页面排版员 | 把数据填进 HTML 模板，生成浏览器能看的页面。 |
| Static CSS/JS | 装修和小交互 | 负责页面样式、确认框、搜索、AI 前端请求等。 |
| Config/env | 配置柜 | 放数据库路径、AI Key、模型、超时时间、密钥等配置。 |

## 2. 为什么说它是服务端渲染单体应用

“服务端渲染”表示：页面主要在服务器里生成 HTML，而不是由浏览器端大型前端框架生成。

一次典型访问是：

```text
浏览器请求 URL
-> Flask 找到对应 Blueprint 和路由函数
-> 路由函数调用 Service 或 Model 查数据库
-> SQLAlchemy 从 SQLite 取数据
-> Flask 把数据交给 Jinja2 模板
-> 模板生成完整 HTML
-> 浏览器显示页面
```

“单体应用”表示：公开页、用户中心、后台、AI 接口、数据库访问都在同一个 Flask 项目中，不拆成多个独立服务。

## 3. 启动时发生了什么

入口是 `run.py`：

```text
run.py
-> 可选加载 .env
-> from app import create_app
-> app = create_app()
-> app.run(debug=True)
```

`create_app()` 在 `app/__init__.py` 中完成几件事：

| 步骤 | 当前代码位置 | 作用 |
| --- | --- | --- |
| 创建 Flask app | `Flask(__name__, instance_relative_config=True)` | 得到应用对象。 |
| 加载配置 | `app.config.from_object(Config)` | 读取数据库、AI、CSRF 等配置。 |
| 初始化扩展 | `db.init_app()`、`login_manager.init_app()`、`csrf.init_app()` | 接入数据库、登录态和 CSRF 防护。 |
| 注册用户加载 | `@login_manager.user_loader` | 根据 session 里的用户 ID 找到当前用户。 |
| 注册蓝图 | `register_blueprints(app)` | 把各模块 URL 接入应用。 |
| 注册错误页 | `register_error_handlers(app)` | 处理 400/403/404/500。 |
| 注册模板 helper | `register_template_helpers(app)` | 给模板提供分页 URL 和 CSRF token。 |

## 4. Blueprint 是怎么分工的

Blueprint 是 Flask 用来拆分路由的机制。当前系统把不同业务入口分成多个 Blueprint：

| Blueprint | 主要入口 | 角色 |
| --- | --- | --- |
| `public` | `/`, `/home`, `/discover`, `/articles`, `/search` | 游客浏览和传统搜索。 |
| `auth` | `/login`, `/admin/login`, `/register`, `/logout` | 登录注册退出。 |
| `user` | `/profile`, `/write`, `/settings`, `/admin/users` | 个人中心、写作、资料、后台用户管理。 |
| `column` | `/columns`, `/my/columns`, `/admin/columns` | 专栏公开浏览、我的专栏、后台专栏启停。 |
| `comment` | `/articles/<slug>/comments`, `/like`, `/favorite`, `/admin/comments` | 评论、点赞、收藏和评论审核。 |
| `article` | `/admin/articles` | 后台文章管理。 |
| `category` | `/admin/categories` | 后台分类管理。 |
| `tag` | `/admin/tags` | 后台标签管理。 |
| `dashboard` | `/admin/dashboard` | 后台仪表盘。 |
| `admin` | `/admin/` | 后台入口跳转。 |
| `ai` | `/admin/ai`, `/ai/*` | AI 状态、写作接口、智能搜索。 |

## 5. 一次用户访问页面的完整协作示例

以游客打开文章详情 `/articles/<slug>` 为例：

```text
1. 浏览器 GET /articles/flask-demo
2. Flask 匹配到 public Blueprint 的 article_detail(slug)
3. article_detail 调用 ArticleService.get_published_by_slug(slug)
4. ArticleService 用 Article 模型查询 SQLite 中已发布文章
5. 如果找不到，abort(404)，走错误页
6. 如果找到，ArticleService.increment_view(article) 增加阅读量
7. 路由把正文拆成 content_blocks 和 toc_items
8. 路由调用 render_template("v041/article_reading.html", ...)
9. Jinja2 把 article、目录、阅读时间等数据填进模板
10. Flask 返回 HTML 给浏览器
```

这个过程体现了四层协作：

| 层 | 例子 | 作用 |
| --- | --- | --- |
| Route | `public.article_detail()` | 接收 URL 和参数，组织流程。 |
| Service | `ArticleService.get_published_by_slug()` | 封装文章查询和阅读量逻辑。 |
| Model | `Article` | 表示数据库里的文章表。 |
| Template | `v041/article_reading.html` | 展示文章阅读页。 |

## 6. 写文章流程如何协作

```text
用户 GET /write
-> user.write_article()
-> 查询分类、标签、我的专栏
-> 渲染 user/write.html

用户 POST /write
-> user._write_article_form()
-> ArticleService.validate()
-> ArticleService.create()
-> 写入 Article 和 ArticleTag
-> 发布则跳转文章详情，草稿则留在编辑页
```

这里 `user/routes.py` 负责登录和页面流程，`article/services.py` 负责文章校验、创建、更新和删除，`models.py` 负责真正的数据结构。

## 7. 管理后台权限如何协作

后台路由大多使用 `@admin_required`：

```text
浏览器访问 /admin/dashboard
-> dashboard.index()
-> admin_required 先检查 current_user
-> 未登录：跳转 /admin/login
-> 已登录但不是管理员：跳转首页并提示
-> 管理员：执行 DashboardService.stats()
-> 渲染 admin/dashboard.html
```

当前管理员判断依赖 `User.is_admin`，它根据 `role == "admin"` 返回结果。用户是否可登录还依赖 `User.is_active`，它根据 `status == "active"` 返回结果。

## 8. AI 接口如何协作

AI 写作接口的基本流程：

```text
写作页 JS 发起 POST /ai/summary 等请求
-> ai/routes.py 检查登录
-> 读取 content 和 article_id
-> AIService.generate_summary()
-> AIService._call() 调用 OpenAI 兼容 Chat Completions API
-> 成功或失败都尝试写入 AiLog 基础日志
-> 返回 JSON 给前端
```

AI 智能搜索的基本流程：

```text
首页或搜索页提交 AI 搜索
-> POST /ai/search
-> AIService.smart_search()
-> 阶段 1：AI 理解意图和扩展关键词
-> 阶段 2：SQL 多关键词候选检索
-> 阶段 3：AI 重排序和理由生成
-> 如果 AI 某阶段失败，部分逻辑会降级到关键词候选
-> 返回 JSON 给前端
```

重要边界：

1. AI 写作接口需要登录。
2. `/ai/search` 是公开 JSON 端点。
3. AI 接口真实成功依赖 `AI_API_KEY`、`AI_BASE_URL`、网络和远程服务。
4. `AiLog` 当前只确认基础写入，不能写成采纳闭环完整。

## 9. CSRF、登录态和配置如何保护系统

| 机制 | 当前实现 | 解释 |
| --- | --- | --- |
| 登录态 | Flask-Login | 登录后浏览器 session 记住用户 ID，后续请求可使用 `current_user`。 |
| 管理员权限 | `admin_required()` | 后台入口必须是管理员。 |
| 普通登录保护 | `@login_required` | 写作、个人中心、评论、点赞、收藏等需要登录。 |
| CSRF | Flask-WTF `CSRFProtect` | 普通 POST 表单防止跨站伪造提交。 |
| AI JSON 豁免 | `@csrf.exempt` | AI JSON 接口豁免 CSRF；安全口径需后续确认。 |
| 环境变量 | `config.py` | AI Key、模型、Base URL、超时等从环境变量读取。 |
| 密码哈希 | `User.set_password()` / `check_password()` | 数据库保存哈希，不保存明文密码。 |

## 10. ADR-002 方案 B 对当前理解的影响

ADR-002 方案 B 的核心意思是：

1. 保留当前 Flask + Jinja2 + SQLAlchemy + SQLite 技术栈。
2. 不直接换成前后端分离、微服务、生产级数据库或复杂 AI 架构。
3. 后续如果需要改路由边界、Service、模型、CSS/JS 或 AI Provider，只能在需求确认、测试保护和 ADR 判断下小步调整。
4. 本轮系统理解只建立事实，不直接进入代码实现。
